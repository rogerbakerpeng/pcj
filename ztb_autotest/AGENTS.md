# AI 工作说明（唯一正本）

> 本文件是所有 AI 工具共用的工作说明。`CLAUDE.md`、`.cursor/rules/` 等只是指向本文件的入口。
> 本文件属于**框架层**，所有项目共用，升级时会被替换，项目里不要改它。**读完本文件后接着读根目录的 `项目规则.md`**（本项目特有的规则）。

本目录是**一个项目**的自动化测试工程：一份 ztb_autotest 对应一个项目，项目信息见根目录 `project.yaml`。推荐与被测系统源码工程放在同一级目录，也可以放在源码工程内部。

> **本文件中的所有路径都相对 ztb_autotest 目录。** 如果会话的工作区是源码工程（ztb_autotest 位于其子目录），读写测试资料时一律在 `ztb_autotest/` 下进行，运行 pytest 前先进入 ztb_autotest 目录。

| 位置 | 内容 |
|---|---|
| `project.yaml` | 项目名称、包含的系统（`systems`）、可选功能开关、源码路径（`source_repos`）、各环境地址与账号、各环境的外部依赖（`deps`）和只读开关（`readonly`） |
| `common/` | 框架代码（框架层，不改） |
| `api/ ws/ pages/ flows/ mocks/ contracts/ fixtures/` | 本项目接入时补全的接口、页面对象、造数方法等（模板层）；页面对象放 `pages/<系统>/`；页面通用方法的学习记录和环境差异登记在 `pages/环境差异.md` |
| `samples/` | **样本库**：接口报文、招标文件、投标文件、文档样本、第三方资料，统一登记在 `samples/index.yaml` |
| `testcases/baseline/<系统>/` | 标准产品基线用例（框架自带，尽量不改） |
| `testcases/features/` | 可选功能用例，`features` 开启才执行 |
| `testcases/modules/<模块>/` | **本项目**按模块沉淀的自动化回归用例和定制用例 |
| `requirements/<日期>_<需求名>/` | 每个需求的确认项、测试用例、验收记录、沉淀记录 |
| `用例库/<模块>.md` | 本项目按模块沉淀的手工用例，反映功能当前行为 |
| `prompts/` | 提示词模板 00 新项目接入、01 需求自查、02 用例与脚本、03 验收后沉淀、研发_源码影响分析、研发_编码与自测 |
| `tools/` | `preflight.py` 准备度检查、`run_req.py` 需求自测运行器（失败摘要、只跑失败、定性、轮次）、`setup_env.py` 安装检查 |
| `docs/需求测试流程.md` | 流程、关卡、需求分级 |
| `docs/源码地图.md` | 项目类型和代码知识来源、公共部分（接入时）、模块到代码位置的索引（做需求时按需积累）；找代码前先读 |
| `docs/流程图.md` | 三张流程图：总览、本地开发环境、测试环境闭环与沉淀 |
| `docs/改进建议.md` | 规则和提示词的改进建议（AI 只追加，人确认后才并入） |
| `docs/各阶段提示词.md` | 给人用的提示词速查：每个阶段对 AI 说什么 |
| `docs/模板/` | 文档模板，如 `03_验收记录模板.md`（含返工分类） |
| `项目规则.md` | 本项目特有的规则，补充本文件；升级不覆盖 |
| `framework.yaml`、`docs/框架升级.md` | 哪些文件是框架层、模板层、项目层；怎么升级 |

AI 在本目录处理三类任务：

- **新项目接入**（每个项目一次）：补全模板层（`api/ ws/ pages/ flows/` 等）和 `project.yaml` 中的 TODO，让产品基线冒烟跑通 → 见下方「新项目接入」
- **需求测试**（每个需求一次）：按**三步法**工作，**第一步和第二步结束后都必须停下，等用户答复后再继续**
- **研发编码与自测**（研发用 AI 编码时）：先按确认项编码（不看用例），用例生成后再按用例运行自动化、修复、出自测报告 → 见下方「研发编码与自测」

## 框架层和项目层（所有任务都适用）

本目录的文件分三层，见 `framework.yaml`：**框架层**（所有项目共用，升级时替换）、**模板层**（框架给初始版本，项目补全）、**项目层**（项目自己的内容）。

1. **不修改框架层文件**：`AGENTS.md`、`prompts/`、`tools/`、`common/`、`conftest.py`、`fixtures/ui_fixtures.py`、框架提供的 `docs/` 等。改了会在升级时被替换掉
2. 需要本项目特有的规则 → 写进 `项目规则.md`；需要页面通用方法 → 写进 `pages/base_page.py`（框架基类 `common/ui_base.py` 不改）；觉得框架本身该改 → 写到 `docs/改进建议.md`，由框架维护者并入下个版本
3. 新建文件放在项目层或模板层的目录里（`pages/`、`flows/`、`api/`、`testcases/modules/`、`requirements/` 等），不要放进 `common/`、`tools/`
4. 用户说「升级框架」时，按 `docs/框架升级.md` 用 `python tools/upgrade.py` 处理，不要手工复制覆盖

## 文档写作通用规则（所有产出文档都适用）

人读不动长文档，越长越容易漏掉问题。所以：

1. **正文只写结论和问题，推理过程放附录**：分析过程、源码依据、日志、比对过程一律放附录，正文用编号引用
2. **有篇幅上限**：

| 文档 | 正文上限 | 其他限制 |
|---|---|---|
| `01_确认项.md` | 120 行 | 问题不超过 15 条；关键场景示例 5～8 行 |
| `02_测试用例.md` | 前三节 80 行 | 只展开 P0/P1；每条详情不超过 8 行 |
| `03_验收记录.md` | 60 行 | 每个问题一句话 |
| `04_沉淀记录.md` | 60 行 | — |
| `自测报告.md` | 60 行 | — |

3. **表格单元格只写一句话**，不用 `<br>`；需要分点的写成小节和列表
4. **先给结论**：每份文档第一节是摘要或结论，读者看完第一节就知道要做什么
5. 超出上限时，删减低价值内容或移入附录，不要压缩成难读的长句
6. **口令放环境变量或 `.env`**：`.env`（参照 `.env.example`）只由人填写；AI 不读取、不输出、不修改 `.env`，缺口令时只说缺哪个变量名
7. **文档里也不写内部地址**：数据库主机、IP、库名不写进报告，写「local 环境（见 project.yaml）」即可
8. **任何文档、脚本、日志摘录中都不写口令**：密码、密钥、带密码的连接串一律不出现，只写环境变量名（如「需设置 `ZTB_DB_PWD`」）；从日志或配置中摘录内容前先去掉口令

## 数据安全规则（所有任务都适用，优先级最高）

开发库和测试环境通常是多人共用的，自动化误删的数据往往无法恢复。

1. **只动自己造的数据**：新增、修改、删除只针对 `AUTO_` 前缀的数据，或 `project.yaml` 的 `test_data` 中登记的专用测试项目
2. **不为复位而破坏已有数据**：用例需要「未生成」「未发送」之类的初始状态时，新造一条数据；不要把已有业务数据删掉或改回去
3. 确实只能使用已有数据时：**先停下来**，说明要动哪张表、哪些记录、为什么，用户确认后才做；先备份、结束后还原，只按主键操作
4. **不执行改表结构的 SQL**（新增字段、建表等）：告诉用户需要执行哪个迁移脚本，由研发手工执行
5. **只读环境只查不改**：`readonly: true` 的环境（测试环境、联调环境）不调用写操作、不复位、不清理、不改配置
6. 框架会拦截危险写操作（`WriteBlocked`：只读环境的写、改表结构、不带 WHERE 的修改删除）。被拦截说明做法不对，**不要绕过**（不要换工具直连数据库、不要拆成多条语句）
7. **界面操作同样会改数据**：有些按钮点一下就会隐式保存（如「生成/编辑」先保存再打开）。界面用例也只在自己造的 `AUTO_` 数据上操作；不要为了避免副作用而在页面里屏蔽保存
8. 做过的数据改动要留痕：在自测报告附录中写明哪张表、多少条、是否已还原

## 外部依赖规则（其他团队的系统、浏览器控件）

评标系统、招标工具、第三方认证由其他团队开发，本地没有；NTKO、签章等是浏览器控件，无法自动操作。统一按下面的方式处理：

| 情况 | 本地 | 测试环境 |
|---|---|---|
| 对方调我们（如评标取数） | 脚本扮演对方直接调我们的接口，自动化 | 可选 |
| 我们调对方（如获取评标结果） | mock 代替对方，覆盖正常和异常场景 | 真实系统，正常流程 1～2 条，只读触发后在页面或接口上核对结果 |
| 浏览器控件 | 控件之前、之后的逻辑自动化；之后的逻辑用样本文件直接调用**我们应用的保存接口** | 控件本身人工验证 |

- 每个环境在 `project.yaml` 的 `deps` 中声明各依赖是 `mock / real / manual / none`；用例用 `@pytest.mark.needs("<依赖>")` 声明依赖，框架据此运行或跳过。**跳过的不算失败**，记为「待测试环境执行」
- mock 只在本地使用，**不要把共用的测试环境指向 mock**
- mock 数据取自真实报文（由研发从测试环境的接口日志或应用日志导出，脱敏后放样本库 `samples/messages/`），不凭理解手写；详见 `samples/README.md`
- 不模拟控件本身，也不因为有控件就把整个场景标成人工：拆成三段，能自动的自动
- 本地自测通过后，仍要在测试环境验证真实对接（`pytest --req <需求目录名> --env test` 加人工清单），之后才算可以交付验收

## 样本库规则

测试用的现成材料统一放在 `samples/`：接口报文（`messages/`）、招标文件和投标文件及文档样本（`files/`）、第三方资料（`third_party/`）。

1. **先读索引再按需读文件**：需要报文、文件或第三方资料时，先读 `samples/index.yaml`，只读本次需求涉及的那几个；加密投标文件等二进制文件不读内容，看索引说明
2. **脚本统一用 `common.samples` 取**：`samples.message(依赖, 接口, 场景)`、`samples.file(id)`、`samples.entries(...)`；不要在脚本里写死文件路径，不要把报文内容抄进脚本
3. **缺样本就向人要**：索引里是 TODO 或没有需要的场景时，在确认项的「测试准备」或用例的「遗留事项」中写明要什么、应放在哪个路径，由人提供；**不要自己伪造文件或报文**。可以先用手写报文让脚本跑通，但来源必须标「手写，待录制」
4. **新增要登记**：新放进来的文件在 `index.yaml` 加一行（来源、说明）；`python -m common.samples` 检查是否一致
5. 样本要脱敏，不放口令和证书私钥
6. **按需提供，不一次要齐**：项目接入时只向人要挡住基线冒烟的最少几样（不超过 5 项）；其余的等某个需求用到时，在该需求 `01_确认项.md` 的「测试准备」里列，只列这个需求要的。不要把所有可能用到的样本一次列成几十项的清单
7. **能自己取的不向人要**：本系统页面接口的请求和返回（**不单独抓**：走页面造数时用 `common.traffic.record` 包住每一步，缺的报文自动录进样本库并登记，见「测试数据与账号准备」）、能访问到的 WSDL。测试环境与外部系统之间的真实报文脚本取不到（测试环境不连库、看不到服务端日志），**用到时**在该需求确认项的「测试准备」里请研发导出，替换「手写，待录制」的样本

## 测试数据与账号准备

用例需要的前置数据（前面流程走到某一步的项目、单位的各种状态）和账号，**默认由自动化自己准备，不因为确认项没写就向人要**。能造什么、怎么造登记在 `flows/造数能力.md`，写用例和脚本前先读它。

**本地开发环境：自己造**

1. 先用 `flows/` 里已有的造数方法；链条不够长时（如已有「发布公告」，本需求要「已发出邀请函」），把新的一段补进 `flows/`，并在 `flows/造数能力.md` 登记，不要只写在本需求的脚本里
2. 造数方式的顺序：业务接口（和页面保存走同一个接口）→ 页面操作 → 直接写库（最后手段，只写 `AUTO_` 数据，并说明绕过了哪些业务逻辑）
   - 接口带防重放签名（如请求里有 `reqtime`、`paramsign` 之类，签名由页面脚本生成）→ 造数直接走页面，不要尝试伪造签名或脱离页面重放
   - **走页面造数的同时录下接口**：每一步用 `with traffic.record(page, "<步骤名>"):` 包住，样本库里缺的报文会自动录进 `samples/messages/trade/` 并登记，不再另跑一遍去抓包；已有的不覆盖，要重录时设置环境变量 `ZTB_RECORD=1`
3. **自己系统的前置数据不用 mock**：mock 只用来代替外部系统。前置数据是假的，后面的业务校验就测不到
4. 同一批账号的不同状态（确认参加、不参加、未回复）用造数实现，不为此注册新账号

**长流程的前置数据**（如标后需求要「已出评标结果」「已定标」的标段）

不全靠模拟走完整流程，也不全靠直接写库，**按步骤选做法**：

| 前面的步骤 | 做法 | 例子 |
|---|---|---|
| 本系统的步骤，没有外部依赖 | 走业务接口 | 计划、公告、报名、邀请函 |
| 外部系统的结果 | 扮演对方：脚本以对方身份调我们的接口；或用本地 mock，再由我们这边触发获取 | 评标结果回写、获取评标结果 |
| 走不通的步骤（要 CA 解密、要真实工具、要等时间到） | **只对这一步**写库快进 | 解密、到开标时间 |

1. **被测环节本身必须走真实业务**：测中标公示，前面可以快进，中标公示这一步不能写库
2. **写库快进要有依据**：先从源码找到这一步的业务方法写了哪些表和字段（或在本地人工走一遍、比对前后的数据差异），照着写全；不能只改一个状态字段——关联数据缺了，后面的环节会报出假问题，也会漏掉真问题。写好后在 `flows/造数能力.md` 登记「绕过了什么」
3. **每个阶段一个直达方法**：`ProjectFlow.reach("<阶段>")` 从头造到该阶段；新阶段接在链尾补，不要在需求脚本里另写一套
4. **一次运行只造一次**：长链路的前置状态，只读的用例共用一份（session 级 fixture）；会改状态的用例各自造
5. **测试环境不造**：每个常用阶段准备一个专用项目（已开标、已出评标结果、已定标……），在 `test_data` 登记入口；缺哪个阶段在确认项「测试准备」里提

**账号：项目接入时建好账号池，需求里复用**

1. 各角色账号在项目接入时每个环境准备一次，写进 `project.yaml` 的 `accounts`；「账号怎么创建」也在接入时学一次，登记在 `flows/造数能力.md`
2. 本地账号池不够（多一家单位、多一个角色）→ 按登记的方法补一个进池子；学过的方法里没有、或要真实 CA、线下审核的 → 列给人
3. 需求任务里不临时摸索怎么注册账号；`flows/造数能力.md` 里没有创建方法、而本需求又缺账号时，停下来说明，由用户决定是先补接入还是提供账号

**测试环境：不自动造，用专用数据**

1. **测试环境只配地址和账号，不配数据库**：脚本一般在本地或跳板机上运行，连不到测试环境的库。测试环境的用例从页面或接口核对结果，不写查库断言；查库的验证放在本地
2. 测试环境是共用的、只读的：不造数、不建账号
3. 需要的前置数据由人准备一次，在 `project.yaml` 的 `test_data` 登记**一个入口**（如专用项目编号），其余信息脚本从入口在页面或接口上查
4. 这一项要在 `01_确认项.md` 的「测试准备」里尽早列出（只列测试环境需要的），不要等到出用例时才提

**什么时候才向人要**：本地确实造不出来（依赖外部系统的真实结果、真实 CA、线下环节），或是测试环境的专用数据和账号。向人要时写明要什么状态的数据、用于哪些用例，一次说全。

## 页面通用方法与环境差异

页面通用方法（登录、菜单、各类控件的操作和取值、提示框、弹窗）在 `pages/login_page.py` 和 `pages/base_page.py`，所有需求共用。学习记录、各环境验证情况、环境差异登记在 `pages/环境差异.md`，写界面脚本或排查界面失败前先读它。

**什么时候学：项目接入时，一次学完；不在需求任务里学**

1. 学习页面通用方法是「新项目接入」的**必做项**，单独一个会话完成，耗时较长（控件种类多时半小时以上）。做完后每个需求直接复用
2. 处理任何需求之前先执行 `python tools/preflight.py --common`。结果是「尚未学习」时：
   - 需求涉及界面（要写界面脚本或跑界面用例）→ **停下来**，告诉用户「页面通用方法还没学习，这是项目接入步骤，请先按 docs/各阶段提示词.md 的 0-2 完成」，不要在需求任务里自己开始学
   - 只有用户明确说「现在就学」时才做，并且先说明「接下来是一次性的项目接入工作，不是本需求的脚本有问题」，学完再回到需求
   - 需求只出确认项、或只有接口和单元测试用例 → 不受影响，继续，并在结尾提醒一句
3. 学习过程要让人看得到进度：开始时列出要学的清单，每学完一类输出一行「已沉淀：下拉框（3/9）」
4. 需求任务里允许的只有**少量补充**：通用方法已学过，但本需求碰到个别没覆盖的控件，或换环境发现差异（见下）。一个需求里要补的通用控件超过 3 类，说明接入没做完，停下来汇报

**在哪个环境学**

1. 优先本地开发环境（local）；没有本地环境时用测试环境（test）。用 `python tools/preflight.py --pick-env` 判断
2. 地址和账号来自 `project.yaml`（项目接入时填写）。两个环境都不可用时，把缺什么原样告诉用户并**停下来等用户提供**：不猜地址、不自己注册账号、不向用户索要口令明文（口令由用户设成环境变量）
3. 在测试环境学习时只浏览和操作控件，**不保存、不提交、不删除、不改数据**；因此学不到的内容记在登记文件里，等有本地环境再补

**发现环境差异时自行沉淀**（不用等用户吩咐）

开发环境和测试环境大体一样，个别细节不同，例如测试环境接了统一登录而开发环境没有。通用方法在一个环境学完，到另一个环境第一次使用时：

1. 界面用例在新环境失败，而同一条在原环境是通过的 → 先判断是不是环境差异：到新环境的真实页面上看一眼（登录入口、控件结构、提示框样式、多出来的页面或弹窗）
2. **是环境差异** → 当场补进通用方法：
   - 按配置分支：在 `project.yaml` 该环境的 `ui` 一节加一个选项，方法里用 `self.ui_option("<选项>", "<默认值>")` 取，默认值是开发环境的做法；不写 `if 环境 == "test"`
   - 在 `pages/环境差异.md` 登记一行（差异点、两边各是什么、处理方式、发现于哪个需求）
   - 不能破坏原环境：改完后在原环境重跑一条用到该方法的用例；跑不了就在验证情况里注明
   - 在自测报告或测试环境验证结果中写一句「沉淀环境差异 E0x：……」
3. **不是环境差异**（同样的页面、同样的操作，结果不同）→ 可能是只在该环境暴露的缺陷或数据问题，按自测失败的四类处理，不要用环境分支绕过去；拿不准就停下来问
4. 通用方法里没有、但新环境需要的东西（如统一登录页、多出来的安全提示弹窗）同样补进通用方法，不要只写在某个需求的脚本里
5. 某个方法在新环境第一次跑通后，在 `pages/环境差异.md` 的验证情况里填上日期
6. `project.yaml` 中只允许为此新增或修改 `ui` 一节的选项；地址、账号、`deps` 等其他配置仍然不改

## 工作效率规则（所有任务都适用）

一次试点中，单个需求的自测用了两个半小时，主要耗在准备不足和重复重跑上。以下规则用来避免：

1. **先确认能开跑再开始**：自测前运行 `python tools/preflight.py --env <环境> --req <需求目录名>`。有 ✘ 就停下来交给人处理，不在会话里临时安装浏览器、配置环境、找测试数据、摸索登录页
2. **用运行器跑用例**：`python tools/run_req.py`。不直接敲 pytest，不用 tail / grep 截取输出，不为了看报错而重跑（读日志文件）；每轮只重跑失败的；全量只在最后跑一次
3. **定性即停、三轮即停**：判定为预期待确认或环境问题的用例，立即用 `--classify` 定性，之后不再重跑；同一条用例连续失败 3 轮就停下来汇报
4. **先冒烟再跑界面**：每个实施点先用接口或查库验证一次确实生效，再跑界面用例
5. **能不走界面就不走界面**：保存、校验、落库、权限用接口或单元测试验证；界面用例只留必须看页面的
6. **看文件用读文件和搜索工具**，不用命令行；同一个文件不反复读
7. **进度可见、可续跑**：每进入新阶段、每次停下前，更新任务清单、输出一行进度、更新 `requirements/<需求>/自测进度.md`；「继续」时先读进度文件，从记录的位置接着做
8. **浏览器**：自动选择已有的浏览器，不执行 `playwright install`；一律无界面运行，不加 `--headed`
9. **需求里不学通用方法，只摸索本需求自己的页面**：登录、菜单、通用控件在项目接入时已学，直接用 `pages/` 里的；本需求页面上新摸清的操作立即写进页面对象；临时脚本放 `.runtime/probe/`

## 源码使用规则

被测系统源码按 `project.yaml` 的 `source_repos` 访问（相对路径相对本目录解析），**只读，绝不修改源码**。`modules` 字段给出模块与源码子工程的对应关系，优先在对应子工程中查找。

**代码知识来源分两种**（`project.yaml` 的 `code_knowledge.type`，项目接入时确定）：

- **历史项目（custom）**：有个性化代码，以本项目源码为主。接入时**不读代码**：看一遍目录结构，把子工程和模块目录对应到业务模块；再找出公共部分（被多个模块引用的公共方法、组件）。都记进 `docs/源码地图.md`
- **新项目（product）**：基本是标准产品，以产品代码知识为主——产品源码（`product.source_path`）或产品代码知识库工具（`product.tool`，如公司提供的 MCP 服务）

查代码的顺序：**`docs/源码地图.md` → 个性化源码 → 产品代码知识 → 问人**。

1. 找代码前先读源码地图，按地图直接去对应位置；地图里没有的，按需求关键词定点查找，不全量扫描
2. 同一个功能个性化源码和产品里都有时，**以个性化的为准**（个性化覆盖产品）
3. 个性化源码里找不到的功能，是产品功能：用产品代码知识查。产品代码知识不可用时，说明「这是产品功能，本项目源码中没有」，靠页面和接口抓包了解，不要凭印象描述产品的实现
4. **地图按需积累**：每个需求查到的模块位置（页面、入口类、服务、主要表）补一行到源码地图第二节；只记位置和名称，不抄代码
5. 改动涉及源码地图第三节的公共部分时，按地图里「被哪些模块使用」列出影响面，在确认项里要求回归
6. 产品代码只读，也不在本项目里修改；需求要改产品功能时，在确认项里列为设计问题（个性化覆盖还是提产品需求）

- `path` 可以是源码总目录，`modules` 可以为空：此时在总目录中按需求关键词（页面名、表名、类名）查找，跳过 `target/`、`node_modules/`、`.git/` 等目录
- 第一步查到本需求所在的子工程后，**自动在 `modules` 中补一行**「业务模块: 子工程相对路径」（已存在则不改），并在汇报中说明补了什么；不改 project.yaml 的其他内容

| 步骤 | 什么时候读源码 | 读什么 |
|---|---|---|
| 第一步 | 优化类需求，回答「现状、影响范围、上下游」 | 相关页面和组件、公共样式和公共方法的引用处、相关接口 |
| 第二步 | 写脚本时确定选择器、接口地址 | 页面模板中的元素文字、class、id、data-testid；接口请求地址 |
| 第二步 | 研发提供了改动差异时 | 改动涉及的文件，补充影响面回归用例 |

- 源码路径未配置或无法访问 → 不要猜测实现，把问题留给研发在确认项中回答，并提示用户可在源码工作区使用 `prompts/研发_源码影响分析.md`
- 从源码得出的结论，在确认项「研发补充」列注明「源码推断：<文件路径>」，仍需研发确认
- 每一步完成后，如果在 git 仓库中，告诉用户本次新增和修改了哪些文件，建议提交一次

## 第一步：产出确认项（不生成用例）

触发：用户提供需求文档，要求分析、出确认项，或说「按流程处理这个需求」。

1. 读取 `prompts/01_需求自查.md`，按其中的测试模型和问题分级（设计 / 阻塞 / 建议）分析需求
   - 用户在需求文档之外粘贴了文字、SQL、模板或截图（即使没有写「个人补充」），一律按模板一的「个人补充的使用规则」处理：先转写截图，再逐条比对，已覆盖的不再提问；需求文档内嵌的截图同样要转写
   - 用户说「精简」或已在补充中说明只关心某些点时，按模板一的【详略】规则输出
2. 优化类需求，先读取现状：`用例库/<模块>.md`、`testcases/modules/<模块>/`、`testcases/baseline/<系统>/` 中相关用例，以及源码（按源码使用规则）
3. 判断需求类型（全新功能 / 历史功能优化）和级别（小 / 中 / 大）
4. 输出 `requirements/<需求>/01_确认项.md`，**严格按模板一的输出格式**：
   - 正文四节：摘要（含**关键场景示例** 5～8 行）→ 待研发答复（设计、阻塞、建议、影响范围）→ 待交付答复 → 测试准备（含提供人）
   - 附录：需求理解详述、现状与源码依据、影响范围明细、附注、设计参考
   - 正文只写结论和问题，推理和源码依据放附录并用编号引用；表格单元格只写一句话
5. 第一步、第二步都**不判断本需求是否已经编码**：读源码只看现有功能；代码写没写，由用户在开始自测时的提示词里说明
6. **停止**，告诉用户：设计问题、阻塞问题各几条，分别由谁回答；最重要的风险是什么；并提醒交付**逐行确认关键场景示例**（这是防止理解偏差最关键的一步）

**设计问题的处理**：按需求实现会导致原有流程断开或出现缺陷时，归为「设计问题」。AI 在可选方案中标出推荐方案，并把方案结论预填为「【默认】按推荐方案 X」；研发审阅，不同意就改，没把握推荐的写「【待定】」由研发选。附录 E 的设计参考仍标明「供研发参考，非结论」。

**默认答复**：确认项中除关键场景示例的「交付确认」列外，所有答复都预填【默认】，人只改不同意的，未修改的【默认】视为同意。

## 第二步：产出测试用例和自动化脚本

触发：用户表示确认项已答复（填在 `01_确认项.md` 的答复处，或在对话中给出）。

1. 检查：关键场景示例是否已逐行确认（✘ 的是否写明了正确预期）、是否还有「【待定】」的方案结论；有未完成的，列出来并停止
   - 保留【默认】的答复视为同意，按默认处理；方案结论为「【待定】」的视为未答复，停止
   - 在 02 摘要中写一句「按默认通过：D01、Q02、S01…；人工修改：…」，便于追溯
2. 读取 `prompts/02_用例与脚本生成.md`
   - **依据是确认项，不是代码**：这一步不用等研发编码，也不检测编码进度、不读本需求新写的代码；读源码只为了解现有功能和现有页面、接口、表的实际名称
   - 脚本要用的信息分三种：现有功能的信息**自己查**；本需求新实现的细节（新字段名、新接口名、新元素的实现方式）写成 `TODO(编码后落地)` 记入附录 D，不问人、不猜候选值；只有需要人决定或提供的才进遗留事项
   - 遗留事项只有三类：预期待确认、设计缺口（这两类同时追加到 `01_确认项.md`，标 🆕）、数据账号环境；超过 5 条说明确认项问得不够，提示先补 01
   - 不写「宽松断言」；测试数据尽量由脚本自己造，`test_data` 只登记最少的入口
3. 读取框架约定：`pytest.ini`、`conftest.py`、`pages/base_page.py`、`pages/环境差异.md`、`project.yaml`，以及该模块已有的页面对象和用例（优先复用，避免重复）
4. 生成前按模板二「第二部分」**11 项自查**：每条关键场景示例都有对应用例、设计方案逐点覆盖（改动公共逻辑必须做原流程端到端回归）、失败路径、确认项要求逐条对应、mock 分层（浏览器层 / 服务端，数据取自真实报文）、数据状态重置、预期可观察、关键改动有断言、依赖标注、待确认不臆测、外部依赖分段、非功能点按需覆盖（权限、敏感数据、操作留痕、历史数据、多入口一致、输入安全）
   - 每条用例标明正向 / 反向、类型，并定好**执行环境**：单元测试 / 本地自动-接口 / 本地自动-界面 / 本地 mock / 测试环境自动 / 测试环境人工；纯逻辑规则优先用单元测试，保存、校验、落库、权限用接口，界面只留必须看页面的；
   - 用例写法：输入值具体、前置条件写明数据怎么来、预期只写能判断对错的唯一结果（不写「布局正常」「无异常」「A 或 B」）、同一验证点不重复；优先级要分出轻重
   - 不能自动化的写明原因（只能是第三方控件、真机或真人、视觉效果、外部系统无法模拟）
   - 脚本中外部依赖用 `needs` 标签声明，数据操作遵守「数据安全规则」
5. 输出，**严格按模板二的输出格式**：
   - `requirements/<需求>/02_测试用例.md`：摘要（含自查结论）→ 研发自测对照 → 用例总览 → 用例详情 → 外部依赖与 mock 方式 → 测试数据与环境 → 测试环境验证清单 → 遗留事项
   - 自动化脚本：页面对象 `pages/<系统>/<模块>_page.py`，用例 `testcases/modules/<模块>/test_<功能>.py`；每条用例同时带 `module("<模块>")` 和 `req("<需求目录名>")` 两个标签
   - 需求涉及多个模块时，由 AI 按模块拆成多个脚本文件，都带同一个 req 标签，拆分结果写在 02 用例总览的「模块」列
   - 新增账号或配置：在 `project.yaml` 中以 TODO 占位
6. **停止**，汇报用例数量（按执行环境、优先级、正反向）、自查发现的风险、需要研发补充的遗留事项

**修订用例**：用户要求评审或修改已有的 `02_测试用例.md` 时，按同一格式输出，新增标 🆕、修改标 ✏️、待确认标 ❓，并在末尾附修改记录（类型｜编号｜内容｜原因）。

## 第三步：验收后沉淀

触发：用户表示「验收通过，沉淀用例」。

1. 读取 `prompts/03_验收后沉淀.md`、`02_测试用例.md`、`03_验收记录.md`
   - `03_验收记录.md` 不存在时，请用户按 `docs/模板/03_验收记录模板.md` 填写；用户口述验收结果时，可按模板生成初稿请用户确认，**每个问题都要标注返工分类**
   - 返工分类为「用例遗漏」「用例错误」的问题补成用例；「需求理解」「设计」类问题，在沉淀记录中提出对检查清单的改进建议
2. 验收中发现、但用例没覆盖的问题，先补成用例
3. 逐条分类：
   - **回归用例**（P0/P1、长期有效）→ 合并进 `用例库/<模块>.md` 对应功能点；已自动化的确认脚本位于 `testcases/modules/<模块>/` 并带 `@pytest.mark.module("<模块>")`
   - **一次性用例**（如只验证一次的样式调整）→ 不沉淀，在沉淀记录中写明原因
   - **与旧用例冲突**（本次需求改变了原有行为）→ 列出旧用例编号和修改建议
4. **修改或删除已有用例、已有脚本之前，先列出清单请用户确认**；新增可以直接写
5. 在模块文件末尾的「变更记录」追加一行
6. 输出 `requirements/<需求>/04_沉淀记录.md`：新增、修改、删除、未沉淀的用例及原因
7. 汇报沉淀结果

## 研发编码与自测

触发：用户说「实现需求 / 编码 / 自测 / 生成自测报告」，或引用 `prompts/研发_编码与自测.md`。

1. 读取 `prompts/研发_编码与自测.md`，顺序为：编码前检查 → 阶段 1 编码 → 自测前检查（`tools/preflight.py`）→ 阶段 2 准备测试支撑（含冒烟自检）→ 阶段 3 自测循环（`tools/run_req.py`）→ 阶段 4 自测报告；部署到测试环境后再做阶段 5 测试环境验证；检查有 ✘ 就停下汇报；用户指定阶段时只做该阶段
   - 阶段 1 新写或改动的对接代码要满足**可测试性**：对方地址可配置、控件保存后的逻辑由我们应用的服务端接口触发；不满足且改动较大时标「可测试性缺口」并停下来问
   - **代码状态由用户在开始自测的提示词里说明**（已编码完成 / 写了一部分 / 还没编码），AI 不自己通读源码去判断；用户没说时只问一次
   - 核对不是每次都要逐点通读源码：用户说已编码完成就跳过；有 git 改动时默认只做快速核对（对照改动文件，只列看不到改动的实施点）；用户要求时才完整核对
   - **阶段 1 是「核对与补齐」，不是从零编码**：先按确认项整理实施点并核对源码现状（已实现 / 部分 / 未实现），输出后直接补未完成的，不停下等确认、不重写已实现的；用户说「已编码完成」时跳过阶段 1
   - 用户不需要提供模块名：本需求用例用 `pytest --req <需求目录名>` 运行，涉及的模块从 02 中读出，用于 `--module` 回归
   - 阶段 1 只依据 01 确认项，不读取 02_测试用例.md 和本需求的测试脚本
   - 02 还没生成时，编码完成后汇报「等待测试用例」并停止
2. 本任务**允许修改源码工程**（仅限与本需求相关的代码），这是对「源码只读」规则的唯一例外
3. **测试是标准**：不修改 `testcases/` 中的断言和预期、不修改 `02_测试用例.md` 的预期、不把失败用例改成 skip 或 xfail、不删除用例。允许的测试改动只有：补全 TODO、删除已实现依赖项的 xfail、实现 mock 和数据重置等支撑代码
4. 自测失败按四类处理：业务代码问题改源码；测试脚本问题改脚本（不改断言）；预期可能有误或需求未覆盖时**停下来**列出，由用户和交付确认；**环境问题（未配置、连不上、登录失败）立即停下来说明缺什么，不改 project.yaml、不猜地址、不反复重跑**
   - 例外：界面用例只在某个环境失败、且原因是该环境的界面或登录方式不同，属于**环境差异**，按「页面通用方法与环境差异」当场补进通用方法并登记，不算环境问题，也不用停
   - 因当前环境不提供外部依赖而跳过的用例不算失败，记为「待测试环境执行」；不要为了在本地跑起来而改标签、改配置或模拟控件
   - 需要改动已有业务数据、执行迁移脚本，或写操作被框架拦截时，停下来由用户确认
   - 「每个阶段结束先汇报」的意思是汇报后停止本次回复，等用户说「继续」
   - 用户说「连续执行，阶段间不停」时进入**连续模式**（准备度检查全部通过后才开始）：阶段结束更新任务清单和自测进度文件、输出一行进度并直接进入下一阶段，一直跑到自测报告；检查不通过、设计未写明、预期与确认项矛盾、环境问题、同一失败 3 轮修不好时仍然停下
   - 依据优先级：01 确认项中的答复和方案结论 > 02 测试用例预期 > 需求原文；确认项已答复的点与需求原文不同不算冲突，不要再问
   - 脚本中的转义、引号、拼写笔误，修正后与 02 预期一致的，可以直接修，在自测报告中列出；改变断言含义的仍须先问
5. 设计方案没写明、需要自行决定的地方，先停下来问
6. 阶段 4 输出 `requirements/<需求>/自测报告.md`；对照 git diff 发现未覆盖的改动，列为「建议补充用例」，不自行修改 02

**建议：用例生成和编码使用不同的会话。** 同一个会话既写用例又写代码，AI 会按同一种理解「出题」和「答题」，理解错了也发现不了。条件允许时用不同的会话，甚至不同的模型。交付和研发是同一个人时：
- 至少把「第二步生成用例」「阶段 1 编码」「阶段 3 自测」放在不同会话中进行
- 编码会话中仍然遵守「不修改断言和预期」的规则
- 关键场景示例和 P0 用例的预期，尽量请另一位熟悉业务的同事抽查一遍

## 沉淀：哪些自动做，哪些等验收

| 沉淀什么 | 什么时候 | 要不要人触发 |
|---|---|---|
| 页面通用方法、环境差异、造数方法、录制的真实报文 | 过程中发现就做 | **不用**，自动 |
| 「本次沉淀」清单和沉淀预案（哪些用例建议入回归） | 生成自测报告时 | **不用**，自动 |
| 用例并入 `用例库/` 和模块回归（第三步） | 交付验收通过后 | **要**，用户说「验收通过」才执行——没验收的预期不能进回归，否则错误的预期会变成以后的标准 |
| 规则和提示词的改进 | 测试环境验证、验收中发现共性问题时 | AI 只在 `docs/改进建议.md` 提建议；人确认后，本项目特有的写进 `项目规则.md`，通用的反馈给框架维护者并入下个版本 |

## 需求任务中的边界（自测时最容易越界的几处）

1. **缺数据不等于可以跳过**：只有「当前环境不提供外部依赖」的用例才允许跳过。因为缺前置数据或缺账号而跳过的，本地能造的必须造出来（见「测试数据与账号准备」）；造不出来的在报告中单列为「未完成」，其中有 P0、P1 时**不满足提测条件**
2. **不用「定性」回避数据问题**：用例因为和别的数据撞名、撞状态而失败，改成用自己造的、名称唯一的数据，不定性为环境问题
3. **不替换页面自身的行为**：页面对象里不注入脚本去改写页面的函数（如改写 `window.open`、屏蔽保存）。下载用 Playwright 的下载事件，新窗口用弹出页事件；`page.route` 只用于拦截外部系统的请求。确实绕不开时，在报告「待交付关注」里写明替换了什么、因此没验证到什么
4. **不改框架代码和配置**：需求任务中不修改框架层文件（见「框架层和项目层」）和 `fixtures/`，`project.yaml` 只允许补 `modules`、`ui` 和本需求的 `test_data` 入口。觉得框架该改的，写到 `docs/改进建议.md`，由人决定
5. **造数脚本要沉淀**：放在 `.runtime/probe/` 的造数脚本是一次性的。自测中造出了可复用的数据状态，就整理成 `flows/` 里的方法并登记到 `flows/造数能力.md`

## 小需求一步到位（例外）

用户明确说「小需求，一步出用例」时，第一步和第二步合并输出；依赖未确认问题的预期结果标注「【待确认】默认理解：……」。

## 规则

- 业务规则不确定时提问，不要自行假设
- 选择器、接口地址、表名不确定时写 `TODO` 并说明需要什么信息，不要编造
- 优化类需求必须要求研发提供影响范围；没有提供时在确认项中列为阻塞问题
- 发现按需求实现会导致原有流程断开的情况，归为设计问题，不能用默认理解带过
- 不修改 `testcases/baseline/` 下的产品基线用例，除非影响范围说明它受本次改动影响，且用户已确认
- 测试数据统一加 `AUTO_` 前缀；不在任何文件中写真实密码、真实单位信息；数据操作遵守「数据安全规则」
- 用例和脚本都是初稿，以交付和研发确认的为准
- 只修改本目录内的文件；源码工程只读（「研发编码与自测」任务除外）
