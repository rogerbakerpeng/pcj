# 各阶段提示词（直接复制使用）

把 `< >` 里的内容换成实际值。`<需求目录名>` 指 `requirements/` 下的目录名，如 `20261110_邀请函新增字段`。
ztb_autotest 放在源码工程内部时，路径前加 `ztb_autotest/`（下面按这种情况写）；工作区就是 ztb_autotest 时去掉这个前缀。

**通用习惯**
- 每个阶段开一个新会话；生成用例、编码、自测尽量不在同一个会话
- 口令放系统环境变量，或写进根目录 `.env`（照 `.env.example` 填，不提交）；不要写在对话里
- AI 停下来问你时，回答问题本身；不要说「改测试让它通过」

| 谁 | 什么时候 | 用哪一条 |
|---|---|---|
| 研发 | 项目第一次用（每个项目一次） | 〇 |
| 交付 | 拿到需求 | 一 |
| 交付 | 填完确认项 | 二（研发同时自己安排编码） |
| 研发 | 用例有了，准备测试 | 四 → 五（在提示词里说明代码状态） |
| 研发或交付 | 部署到测试环境后 | 六 |
| 交付 | 验收通过 | 七 |

**确认项填完之后**

出确认项和出用例都属于需求阶段，这时默认还没有代码，AI 也不会去判断代码写没写。
交付用「二」出用例的同时，研发自己安排编码（手写、另开会话让 AI 写，或者留到自测时让 AI 写，都可以）。

**代码写没写，是在开始自测（「五」）时由你在提示词里告诉 AI 的**，三选一：

| 你在提示词里写 | AI 怎么做 |
|---|---|
| 代码状态：已编码完成 | 不核对，直接补全脚本 TODO → 冒烟 → 跑用例 |
| 代码状态：写了一部分 | 对照 git 改动快速核对，只补没有对应改动的实施点（几分钟），再进入测试 |
| 代码状态：还没编码 | 先按确认项把代码写出来（编码时不读用例，防止照着用例凑），再进入测试 |

三种情况后面都一样：用例失败时，代码问题改代码；脚本问题改脚本但不改断言；**预期可能有误、环境问题停下来问人**；最后出自测报告。

之后：部署到测试环境用「六」验证 → 交付验收 → 用「七」沉淀（用例并入用例库和模块回归、问题标返工分类）。
页面通用方法、环境差异、造数方法这三样不用等到最后，过程中发现就当场沉淀。

## 〇、项目接入（每个项目一次）

**0-1 环境**（人自己在命令行执行，不用 AI）

```bash
cd ztb_autotest
python tools/setup_env.py
pip install -r requirements.txt
```

Windows 上同样执行（`cd` 到 ztb_autotest 所在目录即可）。命令行里中文或 ✔ ✘ 显示成问号不影响结果，可先执行 `chcp 65001`。

**已有旧版本 ztb_autotest 的项目**：不要解压覆盖，按 `docs/框架升级.md` 的「第一次从旧版本升级」用升级脚本。

然后填写 `project.yaml`：项目名称、`systems`、源码路径，以及环境的地址、账号、`deps`：
- 有本地开发环境：填 `local`（取消注释）
- **测试环境只填地址和账号，不填数据库**（脚本一般连不到测试环境的库）
- **测试环境的地址和至少一个账号也要填**：没有本地环境时用它学习页面通用方法，部署后的测试环境验证也要用
- 测试环境和开发环境界面上不一样的地方（如统一登录）可以先不填，AI 发现后会自己补到 `ui` 一节

**0-1b 代码知识来源**（区分历史项目和新项目；轻量，不全量扫描源码）

先在 `project.yaml` 填 `code_knowledge.type`：
- **历史项目，有个性化代码** → `custom`
- **新项目，基本是标准产品** → `product`
- 两种都尽量填上产品代码知识：产品源码路径，或产品代码知识库工具（MCP 服务）的名称，并先在 AI 工具里把它接好

```
先完整阅读 ztb_autotest/AGENTS.md、ztb_autotest/项目规则.md、ztb_autotest/prompts/00_新项目接入.md 的「先做：确定代码知识来源」。
接入项目，做「确定代码知识来源」：
1. 验证产品代码知识可用（用它查一个已知功能，如登录）
2. 历史项目看目录结构：列出子工程和模块目录，判断各对应哪个业务模块，写进 project.yaml 的 source_repos.modules
   和 docs/源码地图.md 第二节（只填到模块目录一级）。只看路径，不打开文件读代码
3. 历史项目找出公共部分（被多个模块引用的公共方法、组件），记到源码地图第三节
页面、类、表的具体位置不提前找，做需求时按需补。源码只读。
```

## 二、出用例和脚本（交付，确认项填完后；不用等研发编码）

用例依据的是确认项，不是代码，所以研发没开始编码也可以做。脚本里依赖新代码的细节（新字段名、新接口名）会留成 TODO，研发编码后在「四、五」里补。

```
先完整阅读 ztb_autotest/AGENTS.md、ztb_autotest/项目规则.md、ztb_autotest/prompts/02_用例与脚本生成.md。
需求 <需求目录名> 的确认项已答复，生成测试用例和自动化脚本初稿。
- 确认项：@ztb_autotest/requirements/<需求目录名>/01_确认项.md
依据是确认项，研发可能还没编码：不要检测编码进度，不要读本需求新写的代码。
现有页面、接口、表的名称自己从源码或页面上查；本需求新实现的细节写成 TODO(编码后落地)，记到附录 D，不要问我。
先检查关键场景示例是否逐行确认、有没有【待定】，有就列出来并停下。
用到的报文和文件先查 samples/index.yaml，没有的列为待提供。测试数据尽量由脚本自己造。
完成后停下，汇报：用例数量（按执行环境、优先级、正反向）、界面用例占比，
以及需要人处理的事项（只列预期待确认、设计缺口、数据账号环境三类，写明各阻塞哪些用例）。
```

汇报里「需要人处理的事项」怎么看：
- **预期待确认、设计缺口**：AI 会同时追加到 `01_确认项.md`（标 🆕），在那里答复；设计缺口要转给研发，会影响编码
- **数据账号环境**：按清单准备
- 超过 5 条，多半是确认项没问全，先回头补 01
- 实现细节（方法名、字段名、怎么置灰）不该出现在这里；出现了就回一句「这些放附录 D，编码后落地」

**修订用例**

```
按以下意见修订 ztb_autotest/requirements/<需求目录名>/02_测试用例.md 和对应脚本：
<逐条写意见>
新增标 🆕、修改标 ✏️、待确认标 ❓，修改记录放附录。
```

## 六、测试环境验证（部署到测试环境后）

```
先完整阅读 ztb_autotest/AGENTS.md、ztb_autotest/项目规则.md、ztb_autotest/prompts/研发_编码与自测.md。

测试环境是共用的、只读的：只触发业务、只查数据，不复位、不清理、不改配置，只用专用测试项目。
对接真实系统的用例失败时，先比对真实返回与样本库中的报文，结构变了就停下来告诉我。
界面用例在本地通过、在测试环境失败时，先到真实页面判断是不是环境差异（如统一登录、多出来的弹窗）：

把结果追加到自测报告的「测试环境验证」一节，并列出需要我人工验证的清单。
```

人工清单（控件、真机、视觉效果）由交付按 `02_测试用例.md` 第七节逐条验证。
