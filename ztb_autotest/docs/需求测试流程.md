# 需求测试一体化流程

适用于纯业务系统（一网通办、统一工作台、交易系统内部功能）。交付兼测试一人负责「需求 + 用例 + 验收」，研发（全栈）负责「编码 + 自动化 + 修复」，双方共用 `prompts/` 下的三个提示词模板。涉及评标等其他团队的系统间交互，另需接口契约和联调。AI 按 `AGENTS.md` 的三步法配合：① 出确认项 → ② 出用例和脚本 → ⑤ 验收后沉淀。

## 流程

| 环节 | 负责人 | 输入 | 输出 | 关卡 |
|---|---|---|---|---|
| ① 需求自查 | 交付 + AI | 需求初稿、截图、历史需求 | `01_确认项.md`（提示词一） | — |
| ② 一次确认 | 交付 + 研发 | 确认项、需求 | 答复后的确认项 + `02_测试用例.md`（提示词二） | 设计问题有方案结论、阻塞问题清零，用例双方认可 |
| ③ 编码 + 本地自测 | 研发 | 编码依据确认项；自测依据测试用例 | 代码、自动化脚本、自测报告 | 本地应执行的 P0/P1 自动化全过，原有回归通过 |
| ③′ 测试环境验证 | 研发部署，交付或研发执行 | 已部署的版本、02 第七节清单 | 自测报告中的「测试环境验证」一节 | 真实对接用例通过；人工清单逐条有结论 |
| ④ 交付验收 | 交付 | 自测报告、测试环境 | 验收结论、验收问题清单 | 无严重问题遗留 |
| ⑤ 上线与沉淀 | 研发 + 交付 | 验收结论、测试用例、验收记录 | 线上验证结果；`04_沉淀记录.md`，更新后的模块用例库和回归用例（提示词三） | 修改或删除旧用例须双方确认 |

- ② 与 ③ 并行：确认项答复完，交付生成用例的同时研发按确认项编码；编码不看用例，用例生成后再跑自动化
- ③ 内部循环：编码 → 跑自动化 → 失败当场修 → 再跑
- ③′ 为什么不能省：本地用 mock 代替其他团队的系统，mock 是按我们的理解做的；真实对接、浏览器控件只有测试环境能验证。测试环境是共用的，只读触发、核对数据，不复位、不清理、不改配置
- ④ 发现问题：回到 ③ 修复，交付复验
- 需求变更：回到 ② 重新确认，同步更新用例和脚本
- 设计问题：确认项中发现「按需求实现会导致原有流程断开」时，由研发给出方案、交付确认，方案写回需求后才进入用例设计
- ⑤ 沉淀：回归用例合并进 `用例库/<模块>.md` 和 `testcases/modules/<模块>/`；一次性用例不沉淀；与旧用例冲突的，确认后修改
- 复盘：漏测问题补充到检查清单和用例库

## 两个环境的分工

| | 本地（研发自测） | 测试环境（部署后） |
|---|---|---|
| 外部系统（评标、招标工具、第三方认证） | mock，数据取自真实报文录制 | 真实系统 |
| 验证什么 | 自己的代码：请求组装、返回解析、落库、异常处理 | 对接是否真的通：地址、鉴权、真实报文 |
| 用例 | 多；异常场景只能在这里测 | 少；每个交互点 1～2 条正常流程 |
| 浏览器控件（NTKO、签章） | 控件前后的逻辑自动化 | 控件本身人工验证 |
| 数据 | 只动自己造的 AUTO_ 数据 | 只读，用专用测试项目 |
| 命令 | `pytest --req <需求> --env local` | `pytest --req <需求> --env test` |

生成 02 测试用例依据的是确认项，不依赖代码，可以和研发编码同时进行；脚本中依赖新代码的细节留成 TODO（02 附录 D），研发编码后在自测准备阶段补全。

每条用例在 02 中定好「执行环境」；当前环境不提供的外部依赖，相关用例自动跳过并标注「转其他环境执行」，不算失败。

## 需求分级

| 级别 | 示例 | 做法 |
|---|---|---|
| 小 | 改文案、改字号 | 可一步出确认项和用例；用例几条，可不写自动化 |
| 中 | 会员实名认证优化 | 完整流程，P0 用例必须自动化 |
| 大 | 新模块、跨系统交互 | 完整流程，必须做影响分析；跨团队接口另做契约和联调 |

## 边测边修规则

1. 自动化用例就是缺陷清单：开发期间自动化失败直接修复，不提缺陷单
2. 研发本地跑当前需求用例；提交后持续集成跑当前需求用例 + 原有回归
3. 只登记交付验收阶段发现的问题，复盘时补进用例
4. 提交验收时附自动化报告，交付不重复执行已自动化的部分

## 人工把关的关卡（只审关键点，不读全部文档）

| 关卡 | 谁审 | 审什么 | 时间 |
|---|---|---|---|
| ① 需求理解 | 交付 | 01 关键场景示例逐行 ✔ / ✘ | 约 5 分钟 |
| ② 设计方案 | 研发 | 01 设计问题的方案结论 | 约 15 分钟 |
| ③ 用例预期 | 交付 | 02 中 P0 用例的预期结果（抽查） | 约 10 分钟 |
| ④ 实际效果 | 交付 | 自测报告 + 研发演示主流程 | 约 15 分钟 |
| ⑤ 代码 | 研发 | git diff 中公共逻辑的改动 | 按改动量 |

前三个关卡在编码之前，挡住代价最大的两类返工：需求理解错、设计缺陷。

## 复盘指标（每月）

- 需求自查发现的问题数
- 验收阶段发现的问题数，**按返工分类统计**（需求理解 / 设计 / 用例遗漏 / 用例错误 / 实现缺陷 / 环境配置），哪类最多就改进对应环节的模板
- 线上漏测数
