# 项目自动化测试工程（ztb_autotest）

**一份 ztb_autotest 对应一个项目。** 每个项目复制一份本目录，项目信息填写在 `project.yaml`。
适用于交易系统（含招投标工具、评标系统交互）、一网通办等业务系统。

## 一、放在哪里

层级不做固定要求，两种方式都可以：

```
方式一：放在源码工程内部（AI 在源码工作区可同时读源码和测试资料）
D:\git\<源码工程>\
├── <源码子工程>...
└── ztb_autotest\                  project.yaml 中 source_repos.path: ..

方式二：与源码工程同级（测试工程独立管理）
D:\git\
├── <源码工程>\
└── ztb_autotest\                  project.yaml 中 source_repos.path: ../<源码工程>
```

放在源码内部时，ztb_autotest 会随源码一起提交；如果暂不希望提交，在源码根目录 `.gitignore` 加一行 `ztb_autotest/`。

## 二、目录结构

```
ztb_autotest/
├── AGENTS.md                 AI 工作说明（唯一正本，所有 AI 工具共用）
├── CLAUDE.md                 Claude 入口 → AGENTS.md
├── .cursor/rules/ztb.mdc     Cursor 入口 → AGENTS.md
├── project.yaml              项目配置：包含的系统、可选功能、源码路径、环境与账号（复制后首先填写）
│
├── requirements/             每个需求一个目录：01 确认项 → 02 测试用例 → 03 验收记录 → 04 沉淀记录
├── 用例库/                   本项目按模块沉淀的手工用例（反映功能当前行为）
├── testcases/
│   ├── baseline/trade/       交易系统产品基线用例（框架自带，尽量不改）
│   ├── baseline/ywtb/        一网通办产品基线用例（待补充）
│   ├── features/             可选功能用例（如评标主动推送），project.yaml 开关控制
│   └── modules/<模块>/       本项目按模块沉淀的自动化回归用例、定制用例
│
├── prompts/                  00 新项目接入、01 需求自查、02 用例与脚本、03 验收后沉淀、研发_源码影响分析、研发_编码与自测
├── docs/                     需求测试流程（含人工把关关卡）、模板（验收记录等）、交互点清单、个性化接口需求模板
├── tools/setup_env.py        环境检查：Python、git、依赖、源码路径
│
├── common/                   配置加载、日志、数据库、XML/SOAP 工具
├── api/  ws/                 交易系统 HTTP 接口、WebService 客户端
├── pages/                    页面对象：base_page 通用封装；pages/trade、pages/ywtb
├── flows/  fixtures/         业务流程造数、共用前置数据
├── mocks/  contracts/        Mock 评标系统、接口契约
├── samples/                  样本库：接口报文、招标文件、投标文件、文档样本、第三方资料，统一登记在 index.yaml
├── client/                   招投标工具冒烟
└── reconcile/  db/  data/    数据对账、造数清理、数据驱动数据
```

## 三、新项目使用步骤

### 1. 复制与配置

1. 把本目录复制到项目中（见「放在哪里」），可改名
2. 填写 `project.yaml`：`name`、`systems`、`source_repos`、环境地址、测试账号
3. 运行环境检查并安装依赖：

```bash
cd ztb_autotest
python tools/setup_env.py                 # git 已有仓库则跳过；有 git 未初始化则自动初始化；没有 git 也能用
pip install -r requirements.txt
# 浏览器不用单独安装：自动使用 Playwright 自带的 Chromium，没有则用本机 Chrome 或 Edge
```

**口令不写进文件**，一律用环境变量：
- 账号密码：`ZTB_PWD_` + 角色名大写，例如 PowerShell `$env:ZTB_PWD_AGENT="xxx"`
- 数据库密码：连接串里写 `${ZTB_DB_PWD}`，再设置 `$env:ZTB_DB_PWD="原始密码"`；密码中的 `@`、`:` 等字符会自动转义，不用手工处理
- 其他地址、密钥也可以写成 `${变量名}`

**环境配置按需检查**：`project.yaml` 里用不到的 TODO 不用管，本次要跑的用例需要什么，缺了才会停下并列出缺项。

**每个环境声明外部依赖**（`deps`）：评标系统、文档控件等在本环境是 `mock`、`real`、`manual` 还是 `none`。本地一般是 mock，测试环境是真实系统；当前环境不提供的，相关用例自动跳过并标注「转其他环境执行」。

**共用环境设为只读**（`readonly: true`）：数据库只查不改、结束后不清理。任何环境下，框架都会拦截改表结构和不带条件的修改、删除。

### 2. 让 AI 自动读到规则

- ztb_autotest 是独立目录、AI 工作区就是它：自动读取，无需处理
- ztb_autotest 在源码内部、AI 工作区是源码工程：在**源码根目录**的 `AGENTS.md` 末尾追加下面一段（没有该文件就新建；这是团队共用文件，追加前和研发确认）：

```markdown
## 自动化测试
测试相关任务（新项目接入、需求确认项、测试用例、自动化脚本、用例沉淀）先完整阅读 ztb_autotest/AGENTS.md 并按其执行。
```

- 不方便修改源码根目录时：每个会话第一句说「先完整阅读 ztb_autotest/AGENTS.md」

验证：新会话中问「用三句话复述你处理需求的步骤」，能答出三步法即生效。

### 3. 新项目接入（每个项目一次）

框架中的接口地址、报文、表名、页面元素都是 TODO，需要从源码补全。对 AI 说：

```
接入项目，先做交易系统 HTTP 接口。
```

AI 会按 `prompts/00_新项目接入.md` 一次做一个子任务，完成后停下，等你确认后再做下一个：

| 系统 | 子任务顺序 | 验证 |
|---|---|---|
| 交易系统 | ① HTTP 接口 → ② 评标交互接口 → ③ 数据库表名 → ④ 页面对象 | 每步给出对应的 pytest 命令，最后 `pytest -m p0` |
| 一网通办 | ① 地址和登录方式 → ② 页面对象 → ③ 实名等级账号准备方式 | 需求用例跑通即可（产品基线待补充） |

每个子任务完成后执行 `git diff` 检查改动，确认后提交。

> 每个阶段对 AI 说什么，直接复制 `docs/各阶段提示词.md` 里对应的那一条。

### 4. 处理需求：三步法

| 步骤 | 你对 AI 说 | AI 产出 | 然后 |
|---|---|---|---|
| 1 | 「按流程处理这个需求，先出确认项。系统：xx，模块：xx」+ 需求文档 | `01_确认项.md` | 交付和研发填写答复 |
| 2 | 「确认项已答复，生成用例和脚本」 | `02_测试用例.md` + 自动化脚本 | 交付审核用例，研发补全 TODO、运行、边测边修 |
| 3 | 「验收通过，沉淀用例」 | `04_沉淀记录.md`，更新用例库 | 确认旧用例的修改和删除 |

需求文档放在 `requirements/<日期>_<需求名>/需求文档.docx`。小需求可以说「小需求，一步出用例」，第 1、2 步合并。

**人工只审关键点**：交付逐行确认 01 的「关键场景示例」（约 5 分钟）、抽查 02 中 P0 用例的预期；研发审设计方案。所有文档正文只写结论和问题，有篇幅上限，推理放附录。验收时按 `docs/模板/03_验收记录模板.md` 记录问题，并标注返工分类，用于每月复盘。

### 5. 研发用 AI 编码与自测

研发用 AI 编码时，**先按 `01_确认项.md` 编码（不看用例），用例生成后再按 `02_测试用例.md` 自测**。确认项答复完就能开工，不用等用例生成。按 `prompts/研发_编码与自测.md` 进行：

| 阶段 | 你对 AI 说 | 产出 |
|---|---|---|
| 编码前检查 | 自动做 | 确认项方案结论、答复、源码路径逐项 ✔/✘ |
| 1 核对与补齐 | 「核对需求 xx 的编码」；已写完就说「已编码完成」跳过 | 实施点核对清单（已实现 / 部分 / 未实现），直接补未完成的 |
| 自测前检查 | 自动做（`tools/preflight.py`） | 配置、服务、数据库、浏览器、登录页、用例脚本逐项 ✔/✘；有 ✘ 交给人处理 |
| 2 准备 | 「为需求 xx 准备测试支撑」 | 补全脚本 TODO、本地 mock、造数；**冒烟自检**：每个实施点先用接口或查库验证生效 |
| 3 自测 | 「运行需求 xx 的用例并修复，直到通过」 | 用 `tools/run_req.py`：只重跑失败的；定性的不再跑；同一条连续失败 3 轮即停 |
| 4 提测 | 「生成需求 xx 的自测报告」 | `requirements/<需求>/自测报告.md`，分三栏：本地已执行、待测试环境自动、待测试环境人工 |
| 5 测试环境验证 | 部署后：「需求 xx 已部署，做测试环境验证」 | 真实对接用例结果 + 人工清单结论，追加到自测报告 |

用例和环境都已就绪时，可以说「连续执行，阶段间不停」，从阶段 1 一直跑到自测报告，只在检查不通过、设计未写明、预期矛盾、环境不通时停下（提示词见 `研发_编码与自测.md` 合并版）。

规则：
- 测试是标准，AI 不能为了通过而修改断言、跳过或删除用例
- 数据安全：只动自己造的 `AUTO_` 数据，不为复位而删改已有业务数据，不执行改表结构的 SQL；需要时停下来由人确认
- 报告和文档中不出现口令
- 本地自测在 `project.yaml` 中配置 `envs.local`，执行时加 `--env local`

### 6. 其他团队的系统和浏览器控件怎么测

| 情况 | 本地 | 测试环境 |
|---|---|---|
| 对方调我们（评标取数） | 脚本扮演对方，自动化 | 可选 |
| 我们调对方（获取评标结果） | mock，覆盖正常和异常 | 真实系统，1～2 条正常流程 |
| 浏览器控件（NTKO、签章） | 控件前后的逻辑自动化 | 控件本身人工 |

mock 数据从测试环境接口日志录制真实报文，不手写；mock 只在本地用，不改共用测试环境的地址。

### 页面通用方法：学一次，换环境自动补

登录、菜单、各类控件、提示框和弹窗的操作方法是所有需求共用的，写在 `pages/login_page.py` 和 `pages/base_page.py`。

- **什么时候学**：项目接入时一次学完，接第一个需求之前必须完成（`python tools/preflight.py --common` 确认）；需求任务里不学，没学就停下来提示
- **在哪学**：优先本地开发环境，没有就用测试环境。`python tools/preflight.py --pick-env` 会告诉你用哪个、缺什么
- **测试环境学习只读**：只浏览和操作控件，不保存、不提交
- **环境差异自动沉淀**：测试环境和开发环境大体一样，细节会不同（如测试环境接了统一登录）。AI 在另一个环境第一次跑界面用例时，发现不一样就补进通用方法，并登记到 `pages/环境差异.md`
- **写法**：差异做成 `project.yaml` 里该环境 `ui` 一节的选项（如 `login: sso`），不按环境名写死

### 前置数据和账号：自己准备

- **本地**：前置流程数据由脚本用业务接口造（`flows/`），账号用接入时建好的账号池；能造什么登记在 `flows/造数能力.md`
- **测试环境**：不造数、不建账号，由人准备一份专用数据，在 `project.yaml` 的 `test_data` 登记一个入口
- 需求用到更靠后的流程阶段时，AI 接着往 `flows/` 里补并登记

### 样本库：测试材料统一放一处

接口报文、招标文件、投标文件、文档样本、第三方资料都放在 `samples/` 下，登记在 `samples/index.yaml`：

| 目录 | 放什么 |
|---|---|
| `samples/messages/<外部系统>/<接口>/` | 录制的请求和返回报文，按场景命名 |
| `samples/files/tender、bid、doc/` | 招标文件、投标文件（正常和各类异常）、Word 和 PDF 样本 |
| `samples/third_party/<名称>/` | 对方团队或厂商提供的接口文档、WSDL、控件保存请求的抓包等 |

人按约定放进来并登记；AI 先读索引再按需读取，缺什么会列清单向人要，不自己伪造。`python -m common.samples` 检查索引和文件是否一致。详见 `samples/README.md`。

### 7. 让自测快起来

试点中单个需求自测用了两个半小时，主要耗在准备不足和重复重跑。现在的做法：

```bash
python tools/preflight.py --env local --req <需求目录名>      # 开跑前一分钟确认：配置、服务、数据库、浏览器、登录页、脚本
python tools/run_req.py --req <需求目录名> --env local        # 跑用例：只给失败摘要，完整输出在日志文件
python tools/run_req.py --req <需求目录名> --env local --failed   # 只重跑失败的
python tools/run_req.py --req <需求目录名> --classify "018=c:预期待交付确认"   # 定性后不再重跑
python tools/run_req.py --req <需求目录名> --status           # 看进度
```

- **人先跑一遍准备度检查**，把 ✘ 处理掉再让 AI 开始；AI 不在自测会话里装浏览器、配环境、找数据
- **浏览器**无界面运行，另起独立进程，不影响你正在用的浏览器；不需要下载
- **登录**每个角色整次运行只登录一次
- **用例分层**：保存、校验、落库用接口或单元测试（每条 1～2 秒），界面只留必须看页面的（每条 20 秒以上）
- **进度**：AI 每换阶段更新任务清单和 `requirements/<需求>/自测进度.md`，会话中断后说「继续」可以接着跑

## 四、运行

```bash
pytest -m p0                      # 冒烟（每次部署后）
pytest -m "not e2e"               # 全量（夜间）
pytest --module 招标计划           # 按模块回归（改了哪个模块就跑哪个）
pytest --req <需求目录名> --env local   # 只跑某个需求的用例（研发本地自测）
pytest --req <需求目录名> --env test    # 部署后在测试环境验证真实对接（只读）
pytest -m e2e --env uat           # 全链路（联调环境）
pytest --alluredir=reports/allure && allure serve reports/allure
```

运行时自动筛选：只运行 `systems` 中列出的系统基线；可选功能未开启时不加载；依赖的外部系统在当前环境不提供时跳过，并在结果末尾汇总。

Mock 评标服务（交易系统 ② 获取评标结果）在**本地**单独启动，本地应用的评标接口地址指向它：

```bash
python -m mocks.eval_mock_server --host 0.0.0.0 --port 18080
```

## 五、不同 AI 工具

规则只维护在 `AGENTS.md`，其他入口文件都指向它。

| 工具 | 读取方式 |
|---|---|
| DeepSeek Harness | 从项目根目录（以 `.git` 为标记）到当前目录读取 `AGENTS.md`、`CLAUDE.md`，子目录中的文件在读写到该目录时才加载；不解析 `@` 引用 |
| Claude Code | 读取 `CLAUDE.md`（内含 `@AGENTS.md` 引用） |
| Codex、Cursor 等 | 读取 `AGENTS.md`；Cursor 另有 `.cursor/rules/ztb.mdc` |
| GitHub Copilot | 只读取仓库根目录的 `.github/copilot-instructions.md`，在其中写一句「测试任务先阅读 ztb_autotest/AGENTS.md」 |
| 其他 IDE 插件（通义灵码、Trae、CodeBuddy 等） | 在工具的「项目规则」中加一句：测试任务先阅读 ztb_autotest/AGENTS.md |
| 网页对话（不读目录） | 上传 `AGENTS.md`、对应的 `prompts/` 模板、需求文档和相关模块用例库 |

> 各工具对规则文件的支持会随版本变化，接入时请以该工具的最新文档为准。

## 六、多个项目

每个项目各一份，互相独立。框架层（`AGENTS.md`、`prompts/`、`tools/`、`common/` 等）所有项目共用、项目里不改；项目内容在模板层和项目层（`project.yaml`、`项目规则.md`、`pages/`、`flows/`、`requirements/`、`用例库/`、`testcases/modules/` 等）。框架升级用 `python tools/upgrade.py`，**不要用新版覆盖**，见 `docs/框架升级.md`。

> 报文、截图、需求文档请先脱敏：单位名称、统一社会信用代码、电话、报价替换为假值，保留结构不变。

### 代码知识：历史项目和新项目不一样

- **历史项目**（有个性化代码）：接入时只看目录结构（子工程、模块目录对应哪个业务）并找出公共部分，不读代码；模块的代码位置做需求时按需记进 `docs/源码地图.md`
- **新项目**（基本是标准产品）：接入产品代码知识（产品源码，或公司的产品代码知识库工具）
- 在 `project.yaml` 的 `code_knowledge` 里声明；查代码的顺序是 源码地图 → 个性化源码 → 产品代码知识 → 问人

### 框架升级：只换框架，不动项目内容

文件分三层（见 `framework.yaml`）：框架层（规则、提示词、工具，所有项目共用）、模板层（配置、页面方法、造数方法，项目会补全）、项目层（需求文档、沉淀的用例、样本文件）。
升级用 `python tools/upgrade.py <新版本.zip>`，不要解压覆盖。项目特有的规则写在 `项目规则.md`。详见 `docs/框架升级.md`。

### 流程图

整体流程见 `docs/流程图.md`（三张图：总览、单个需求在本地、测试环境闭环与沉淀），图片在 `docs/流程图/`。
