# 提示词模板二：生成测试用例和自动化脚本初稿

使用人：需求确认后使用，**不用等研发编码**。用例部分交付审核；脚本是初稿，依赖新代码的细节留到研发编码后落地。
产出物：用例保存为 `requirements/<需求名>/02_测试用例.md`；页面对象放 `pages/<系统>/`，用例放 `testcases/modules/<模块>/`。
前提：`01_确认项.md` 中的设计问题、阻塞问题已全部答复。

````markdown
## 开始前：分清「依据什么」

用例和脚本的依据是**确认项**（业务规则和设计方案），不是代码。研发可能还没开始编码，这是正常的：

1. **不检测编码进度**：不去判断本需求的代码写没写、写到哪了，不读本需求新写的代码，不因为「代码还没有」而停下或提问
2. **读源码只为两件事**：现有功能怎么工作的（用于影响面用例和复用已有页面对象）；现有页面、接口、表的实际名称
3. 用例的预期只写确认项里定下来的、从外部看得到的结果，本来就不依赖代码怎么写
4. 脚本里需要的信息分三种，处理方式不同，**不要都列成问题丢给人**：

| 信息 | 例子 | 怎么处理 |
|---|---|---|
| 现有功能的信息 | 已有列表的字段名、已有页面的入口地址、已有接口 | **自己查**：读源码，或在已学习页面通用方法的环境打开页面看；查不到的归到下一类 |
| 本需求新实现的细节 | 新接口的方法名和字段名、新按钮怎么置灰、新页面地址 | **不问、不猜候选值**：在页面对象里写成 `TODO(编码后落地)`，断言照常按预期写；记入附录 D「编码后落地清单」，研发编码后在自测准备阶段补全 |
| 需要人决定或提供的 | 预期到底是哪种、缺账号、缺专用测试项目 | 列入第八节遗留事项，见下面的规则 |

5. **遗留事项只收需要人处理的事**，每条写明阻塞哪些用例。只有三类：
   - **预期待确认**：确认项没定、两种理解都说得通 → 追加到 `01_确认项.md` 的问题中（编号接着排，标 🆕），对应用例预期标 ❓、脚本标 `xfail(reason="待确认 Qxx")`。**不许写「宽松断言」让两种结果都通过**
   - **设计缺口**：写用例时发现要达到确认项的预期还得多改一处代码，而确认项没提（如下载文件名要按新规则，现有下载接口做不到）→ 同样追加到 01，标 🆕，这会影响研发编码，要尽早让人看到
   - **数据、账号、环境**：造不出来、必须人提供的
   超过 5 条时，在摘要里写一句「确认项遗漏较多，建议先补 01 再继续」——遗留事项多通常说明第一步问得不够，而不是第二步该多问
6. **前置数据和账号自己准备，不因为确认项没写就向人要**：先读 `flows/造数能力.md`。
   - 本地：用 `flows/` 已有方法造；链条不够长就在 `flows/` 里补一段并登记。自己系统的前置数据不用 mock（mock 只代替外部系统）
   - 账号用账号池里的；同一批账号的不同状态靠造数实现。池子不够时按登记的创建方法补；没有创建方法就列入遗留事项
   - 测试环境不造数：需要的专用数据列入遗留事项，写明要什么状态、登记哪个入口
   - 需要前面流程的数据（如标后需求）：用 `section_at("<阶段>")` 取，只读用例共用一份、会改状态的用 `shared=False`；
     缺的阶段在附录 D 记一行「补 ProjectFlow 的 <阶段>」，由研发自测准备时按「长流程的前置数据」规则补全。被测环节本身不能写库快进
7. **测试数据尽量自己造**：用例需要的数据优先由脚本用接口新造（`AUTO_` 前缀）。必须用已有数据时，`project.yaml` 的 `test_data` 只登记**最少的入口**（如一个专用测试项目的编号），其余的（各包名称、单位、附件标识）由脚本从这个入口查出来；不要让人逐个填十几个键

## 第一部分：用例设计

1. 设计方法：等价类、边界值、状态迁移、判定表、场景法，按需求选用
2. 用例分三类：
   - 变更点：验证本次需求的新行为
   - 影响面：根据影响范围和设计方案，验证没有改坏别的功能
   - 不变项：需求明确不变的行为（如 PC 端保持原样）
3. 优先级：P0 主流程 / P1 核心规则 / P2 边缘场景。要真正分出轻重：P0 一般不超过三分之一，不能全是同一级
4. 每条用例标明**正向 / 反向**（反向＝非法输入、无权限、异常状态、失败分支）和**类型**：功能 / 接口 / 权限安全 / 数据（历史数据、一致性）/ 兼容 / 性能，默认功能
5. 执行环境（每条用例必须定好在哪里测，写用例时就定，不要等跑不通才发现）：
   - **单元测试**：纯逻辑规则（校验、计算、判定、取值，如「领取时间不少于 5 日」），不需要页面和环境就能验证；写在源码工程的单元测试中，最便宜也最稳定，能用就优先用
   - **本地自动**：不依赖外部系统，研发本地自测即可。必须注明走哪一层，写成「本地自动-接口」或「本地自动-界面」：
     接口层每条 1～2 秒，界面层每条 20 秒以上，界面用例多了，研发每改一处都要等几分钟
     - 保存、校验、落库、状态流转、权限拦截 → **接口**（直接调后端接口再查库或查返回）
     - 只有必须看页面的才走**界面**：字段位置、回显、弹窗文案、按钮显隐、多步页面交互
     - 一个场景可以拆开：规则用接口验证多组数据，界面只留一条主流程确认页面接通
   - **本地 mock**：依赖外部系统，本地用 mock 代替；异常场景（超时、报错、对方未完成）只能在这里测
   - **测试环境自动**：对接真实外部系统，只读触发后在页面或接口上核对结果（测试环境不连数据库，不写查库断言）；每个交互点 1～2 条正常流程即可
   - **测试环境人工**：浏览器控件本身、真机、真人操作、视觉效果
   一个场景可以拆成多条用例分别放在不同环境（如控件前后的逻辑放本地，控件本身放测试环境人工）
6. 纯逻辑规则（校验、计算、判定、取值）没有安排单元测试的，在「依赖」列写明原因（只能是：项目没有单元测试框架 / 逻辑在前端页面或存储过程里 / 逻辑与界面耦合无法单独调用）
7. 不能自动化的用例必须写明原因，只能是以下之一：第三方控件 / 真机或真人 / 视觉效果 / 外部系统无法模拟。
   「缺少数据」「页面不好操作」不是理由：缺数据就造数据，页面无法复现就降到接口层或单元测试验证
8. 用例写法：
   - **输入值要具体**：步骤中写出实际输入（如标段编号 `AUTO_BD001`、不存在的编号 `NOTEXIST999`、特殊字符 `<>?*%"`），不写「输入有效的编号」
   - **前置条件写明数据怎么来**：新造（写明造什么）或指定专用测试数据；不写「已知某条记录」「系统中存在数据」
   - **预期只写能判断对错的结果**，一个预期只有一种正确结果。不写「页面布局正常」「系统无异常」「数据正确」「条数与预期一致」；不写「A 或 B」——两种都可能时先向交付确认是哪一种
   - **不重复**：同一个验证点只保留一条；同一规则的多组输入合并成一条数据驱动用例

## 第二部分：生成前必须逐项自查（输出时在摘要中说明每项结论）

1. **设计方案逐点覆盖**：设计方案的每个实施点至少对应一条用例；方案改动了公共逻辑（抽公共方法、改公共组件、改公共样式）时，必须补充**原有流程的端到端回归**，验证到最终结果（如落库、状态变化、回调），不能只验证入口还能打开
2. **失败路径**：每个主流程至少有一条失败或异常用例（第三方返回失败、校验不通过、超时、中途放弃、重复提交）；在摘要中给出正向、反向各几条，反向为 0 或明显偏少时说明原因
3. **确认项要求逐条对应**：01 确认项中**每条关键场景示例（E01…）必须对应至少一条 P0/P1 用例**，预期以交付确认的结果为准；写明「需要覆盖」的场景、每条默认理解，都要有对应用例或写明不覆盖的原因
4. **mock 分层**：
   - 只验证前端行为 → 浏览器层 mock（Playwright 拦截请求）
   - 涉及服务端调用第三方、落库、回调 → 必须服务端 mock（本地启动 mock 服务，本地应用的第三方地址指向它）；浏览器拦截会让服务端根本不被调用
   - mock 只在本地使用，**不要求把共用的测试环境指向 mock**
   - mock 数据取自样本库的真实报文（`samples/messages/<依赖>/<接口>/<场景>.resp.xml`），不凭理解手写；样本库里没有需要的场景时列入遗留事项，写明要哪个接口的哪个场景、应放的路径，可先手写并注明「手写，待录制」
   - 每条用例注明用哪一层
5. **数据状态**：会改变数据状态的用例（升级、审核、落库）必须写明执行前的重置方式，保证可以重复执行
6. **预期可观察**：预期写成可以直接验证的结果（页面文字、接口参数、记录条数、调用次数），不写实现细节（如「先删标记再处理」）
7. **关键改动有断言**：设计方案的核心参数或标记（如新增的请求参数）要在用例中直接断言
8. **依赖标注**：依赖未完成的方案实施的用例，标明依赖项，脚本中用 `pytest.mark.xfail(reason=...)` 标记
9. **待确认不臆测**：方案中没写明的行为，预期标注「❓ 需研发确认」，不要自行假设
10. **外部依赖分段**：涉及其他团队系统或浏览器控件的场景，按下面的方式拆用例，并保证每个交互点两类环境都有覆盖：
   - 对方调我们（如评标取数）：脚本扮演对方直接调我们的接口 → 本地自动
   - 我们调对方（如获取评标结果）：正常和异常场景 → 本地 mock；正常流程 1～2 条 → 测试环境自动（只读触发、核对数据、用契约校验真实返回）
   - 浏览器控件（NTKO、签章）：控件之前（打开的地址、参数、按钮状态）→ 本地自动；控件本身 → 测试环境人工；控件之后（落库、后续校验）→ 本地自动，用样本文件直接调用**我们应用的保存接口**。保存接口无法直接调用时，列入遗留事项「可测试性缺口」，不要把整个场景都标成人工
11. **非功能点按需覆盖**（需求涉及时才写，不为凑数；不涉及的在摘要中写「不涉及」）：
   - 权限：无权限的角色看不到入口，直接访问地址也被拦截
   - 敏感数据：姓名、证件号、联系方式等的展示脱敏和存储方式（需求或现有规范有要求时）
   - 操作留痕：新增、修改、删除是否记录操作人、时间、内容（需求或现有规范有要求时）
   - 历史数据：上线前已存在的数据在新逻辑下是否正常（优化类需求必须考虑）
   - 多入口一致：同一数据从不同入口进入，看到和保存的结果一致
   - 输入安全：查询条件、文本框输入特殊字符不报错、不被当作脚本或 SQL 执行（预期写成可观察的结果，如「列表为空，页面无报错弹窗」）

## 第四部分：自动化脚本初稿

只为执行环境是「本地自动-接口 / 本地自动-界面 / 本地 mock / 测试环境自动」的用例生成（「单元测试」的用例不在这里写脚本，由研发在源码工程中实现，02 第二节对照表中写明建议放在哪个类），要求：
1. 页面对象：`pages/<系统>/<模块>_page.py`，封装定位和操作；登录、菜单、通用控件直接用 `pages/login_page.py`、`pages/base_page.py` 里已学好的方法，不在需求里重学。`python tools/preflight.py --common` 显示「尚未学习」时，界面脚本先不写，停下来请用户完成项目接入
2. 用例文件：`testcases/modules/<模块>/test_<功能>_api.py`（接口）、`test_<功能>_ui.py`（界面）
3. 接口和界面用例分文件放（`test_<功能>_api.py`、`test_<功能>_ui.py`），分别加 `@pytest.mark.api`、`@pytest.mark.ui`；
   界面用例用 `page_as("<角色>")` 取得已登录的页面（每个角色整次运行只登录一次），不要在每条用例里自己登录；接口用例用 `login_as("<角色>")`
   每条用例标注 `@pytest.mark.p0/p1/p2`、`@pytest.mark.module("<模块名称>")` 和 `@pytest.mark.req("<需求目录名>")`，函数注释写用例编号
   - 需求目录名即 `requirements/` 下的目录名，如 `20261102_评审部废标公告模板调整`
   - 模块名用 `用例库/` 中已有的业务模块名（中文，如「废标公告」），不要用源码子工程名；新模块先在 02 摘要中说明
   - **复杂需求按模块拆分**：一个需求涉及多个模块时，每个模块一个脚本文件，放在各自 `testcases/modules/<模块>/` 下，都带同一个 req 标签；跨模块的端到端用例放在主模块下并标 `integration`；拆分结果写在 02 第三节「模块」列
4. 定位优先使用文字、label、placeholder、data-testid，不用绝对 XPath
5. 移动端用例使用 Playwright 设备模拟（如 iPhone 13、Pixel 7），需要按 UA 判断时确认 UA 已模拟
6. 浏览器层 mock 用 `page.route`；服务端 mock 通过 fixture 控制 mock 服务的场景，不在用例里写死
7. **外部依赖用标签声明**，框架按环境决定运行或跳过，不要在用例里自己判断环境：
   - 本地 mock 用例：`@pytest.mark.needs("<依赖>", mode="mock")`
   - 测试环境自动用例：`@pytest.mark.needs("<依赖>", mode="real")`
   - 两种环境都能跑的：`@pytest.mark.needs("<依赖>")`
   - 用到特定配置项的：`@pytest.mark.needs_config("trade.fetch_ws_url")`；取配置用 `common.config.require(env, "a.b")`，不要直接 `env["a"]["b"]`
   - 依赖名用小写英文（eval、ntko、wzt…），新依赖在 02 第五节说明，并在 `project.yaml` 各环境的 `deps` 中以注释占位
8. **数据安全**（违反会破坏他人数据）：
   - 只新增、修改、删除**本用例自己造的数据**（`AUTO_` 前缀），或 `project.yaml` 的 `test_data` 中登记的专用测试项目
   - **禁止为了复位而删除或修改已有业务数据**；需要「未生成」「未发送」等初始状态时，新造一条数据，而不是把已有数据改回去
   - 确实只能用已有数据时：先在遗留事项中说明，由研发确认；fixture 必须先备份、用例结束后还原，且只按主键操作
   - 「测试环境自动」的用例不用 `db`（测试环境不配数据库），结果从页面或接口取；只读，不做复位和清理（框架在只读环境会拦截写操作，不要绕过）
   - 不通过自动化改表结构；需要新增字段时写进遗留事项，由研发执行迁移脚本
9. 现有功能的选择器、接口地址、表名自己查清再写；本需求新实现的细节写成 `TODO(编码后落地)` 并记入附录 D，不猜候选值、不为兼容几种可能的实现而写多套判断；脚本和文档中不写口令，只写环境变量名
   - 报文和文件统一从样本库取：`from common import samples`，用 `samples.message(...)`、`samples.file("<编号>")`；不要写死路径，不要把报文内容抄进脚本，不要自己生成投标文件之类的样本
10. 断言要对应用例的预期结果，不要只判断页面打开成功
11. 脚本写完后执行 `pytest --req <需求目录名> --collect-only -q` 确认能收集；断言中的正则用原始字符串（换行写 `r"\n"`，不要写 `r"\\n"`），并用 02 中的预期文本在本地自测一次断言能命中
````
