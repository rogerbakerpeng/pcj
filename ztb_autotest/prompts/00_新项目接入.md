# 提示词模板零：新项目接入（补全基线 TODO）

使用人：研发或交付，每个项目一次。ztb_autotest 复制到新项目后，框架中的接口地址、报文、表名、页面元素都是 TODO，需要从源码中补全，产品基线冒烟才能跑通。

**用法**：工作区选源码工程（或 ztb_autotest，并确保 AI 能读到源码），**每个子任务开一个会话**，完成一个、验证一个、提交一个。

> 能读取 ztb_autotest/AGENTS.md 的 AI 工具，直接说「接入项目，先做交易系统 HTTP 接口」即可，下面的提示词会自动被使用；网页对话等不读目录的工具，复制对应提示词使用。

---

## 先做：确定代码知识来源（轻量，不全量扫描源码）

AI 要知道「功能现在是怎么实现的」。项目分两种，来源不同：

| 项目类型 | 特点 | 代码知识来源 |
|---|---|---|
| **历史项目**（`type: custom`） | 有个性化代码 | 本项目源码为主；个性化里没有的功能是产品功能，再查产品 |
| **新项目**（`type: product`） | 基本是标准产品 | 产品代码知识：产品源码，或公司的产品代码知识库工具（MCP 服务） |

先在 `project.yaml` 填 `code_knowledge`。用产品代码知识库工具的，先在你用的 AI 工具里把这个 MCP 服务接好。

**不全量扫描源码**：一个需求只涉及一两个模块，提前读完整个工程又慢、AI 也记不住。
历史项目**默认只看目录结构**（子工程和模块目录叫什么、在哪），不打开文件读代码；具体到页面、类、表的位置，做需求时查到一处记一处（`docs/源码地图.md`）。
接入时做这几件事：

```markdown
任务：确定代码知识来源。只修改 ztb_autotest/docs/源码地图.md，源码只读。
先读 project.yaml 的 code_knowledge 和 source_repos；type 仍是 TODO 时停下来问我项目属于哪一种。
1. 验证产品代码知识可用：有 product.source_path 就看路径能否访问；填了 product.tool 就用它查一个已知功能（如登录），
   确认能查到类名或页面；都不可用时告诉我，并说明「产品功能只能靠页面和接口抓包了解」，不要凭印象描述产品实现
2. 历史项目：**看目录结构**（默认做，只看路径不读代码）
   - 列出 source_repos 下的子工程，每个子工程往下看到模块一级的目录或包名（一般 2～3 层，看出业务模块名为止）
   - 按目录名、包名判断各对应哪个业务模块，写进 project.yaml 的 source_repos.modules（「业务模块: 子工程相对路径」）
     和源码地图第二节（只填「业务模块｜子工程｜模块目录」，页面、类、表留空，做需求时再补）
   - 看不出对应哪个业务的目录，记到第四节，不要猜
   - 跳过 target/、node_modules/、.git/、编译产物、第三方库、静态资源目录；不打开文件、不统计代码
3. 历史项目：找出**公共部分**——被多个模块引用的公共方法、公共页面组件、公共样式和脚本，
   记到源码地图第三节（名称、位置、被哪些模块使用）。这是影响面分析最容易漏的地方。
   找法：看公共目录（如 common、outmethod、公共 js/css）和被引用次数多的类；不逐个模块通读，不建完整的模块地图
4. 填源码地图第一节：项目类型、个性化源码位置、产品代码知识来源、验证结果
完成后汇报：产品代码知识是否可用、识别出多少个子工程和业务模块、找到多少个公共部分、有什么看不出来的。
```

之后查代码的顺序：**源码地图 → 个性化源码 → 产品代码知识 → 问人**。每个需求查到的模块位置由 AI 补进地图第二节。

## 必做：页面通用方法（最先做，所有系统都要）

每个项目只做一次，**必须在接第一个需求之前完成**。不做的话，第一个带界面的需求会在自测时临时摸索登录页和控件，
很慢，而且看起来像是脚本出了问题。耗时较长（控件种类多时半小时以上），单独开一个会话做。

**在哪个环境学**：优先本地开发环境；没有本地环境时用测试环境。先执行：

```bash
python tools/preflight.py --pick-env
```

它会告诉你用 local 还是 test，以及缺什么。两个环境都不可用时，按提示补上其中一个再开始：
- 优先 local：启动本地工程，在 `project.yaml` 取消 local 一节的注释，填地址和账号
- 没有本地环境：在 `project.yaml` 的 test 一节填测试环境地址和一个账号
- 密码不写进文件，用环境变量 `ZTB_PWD_<角色大写>`

```markdown
任务：学习并沉淀页面通用方法。只修改 ztb_autotest 目录（不改框架层文件，见 framework.yaml），源码只读。
1. 执行 python tools/preflight.py --pick-env，按它的结论选环境；两个环境都不可用时，
   把输出原样告诉我并停下，由我提供地址和账号，不要猜地址、不要自己注册账号
2. 先读 pages/环境差异.md、pages/login_page.py、pages/base_page.py，已有的方法不重复学
3. 结合前端源码和真实页面，学习并写进通用方法（定位优先用文字、label、placeholder、data-testid，不用绝对 XPath）：
   - 登录（含验证码的处理方式）、进入菜单、切换到内容 iframe
   - 本项目界面框架的控件操作：文本框、下拉框、单选、复选、日期和日期范围、表格选中行、按钮、页签
   - 读取结果：字段当前值、必填或校验提示、弹出提示框的文字、确认框的确认和取消、弹窗的打开和关闭
   每个方法在真实页面上验证过再写入；浏览器无界面运行，不下载浏览器；临时脚本放 .runtime/probe/
4. 在测试环境学习时（共用环境）：**只浏览和操作控件，不保存、不提交、不删除、不改任何数据**；
   需要保存后才能看到的东西（如保存成功的提示）不学，记到 pages/环境差异.md「没学到的」里
5. 登录方式与默认不同时（如测试环境走统一登录）：在 pages/login_page.py 增加对应的 _login_<方式> 方法，
   在 project.yaml 该环境的 ui.login 声明，并登记到 pages/环境差异.md
6. 更新 pages/环境差异.md：学习记录一行；各方法在本环境的验证情况
7. 补全 pages/<系统>/ 下基线页面对象的 TODO
8. 开始时先列出要学的清单；每学完一类输出一行进度，如「已沉淀：下拉框（3/9）」
完成后汇报：在哪个环境学的、沉淀了哪些方法、哪些没学到及原因、修改清单和验证命令。
```

验证：`python tools/preflight.py --common` 显示「已学习」；`python tools/preflight.py --env <学习用的环境>`（登录页对象、浏览器、服务都应为 ✔），再 `pytest testcases/baseline/trade/ui/test_plan_ui.py --env <学习用的环境>`

> 这一步做扎实，后面每个需求的自测能省下大量时间：一次试点中，没有通用方法时，单个需求为摸索页面写了三十多个临时脚本。

**之后会自动补充**：通用方法在一个环境学完后，到另一个环境第一次使用时（通常是需求的测试环境验证阶段），
发现不一样的地方由 AI 当场补进通用方法并登记，不需要单独再做一次接入。规则见 `AGENTS.md`「页面通用方法与环境差异」。

## 必做之二：账号池和造数主流程

和页面通用方法一样，每个项目做一次。不做的话，每个需求都会因为「缺某个状态的项目」「缺账号」停下来向人要数据。

```markdown
任务：准备账号池和造数主流程。只修改 ztb_autotest 目录（不改框架层文件，见 framework.yaml），源码只读。在本地开发环境做；没有本地环境时只做第 1 步并说明。
1. 账号池：列出本项目用到的角色（如招标人、代理、监管、投标人 3 个），核对 project.yaml 中 local 和 test 的 accounts；
   缺的列出来。本地缺的账号按第 2 步学到的方法创建；测试环境缺的列给我，不要在测试环境创建账号
2. 学习「本地怎么创建账号」：从源码找注册、审核、开通角色的接口或表，在本地实际创建一个验证能登录，
   写成 flows/account_flow.py 中的方法；需要真实 CA 或线下审核、创建不了的，写明原因
3. 造数主流程：从源码和页面学习最常用的前置流程（接口带防重放签名的直接走页面造数），
   走页面的每一步用 common.traffic.record 包住，页面接口报文会自动录进样本库并登记，**不要另外安排抓包**；
   补全 flows/project_flow.py 的 TODO，每一段可以单独调用，并能用 reach("<阶段>") 直达（如：已审核的计划 → 已发布公告 → 已上传投标文件 → 已开标 → 已出评标结果 → 已定标）。
   走不通的步骤（CA 解密、等开标时间）只对这一步写库快进，照源码把这一步写的表写全，登记绕过了什么。
   优先用业务接口；接口走不通的用页面操作；直接写库是最后手段，只写 AUTO_ 数据并说明绕过了什么
   本地没有部署的环节（如某个子系统没起）到此为止，记为「本地造不了」
4. 登记到 flows/造数能力.md：账号池、账号怎么创建、每个阶段能不能造及验证日期
5. 密码不写进任何文件，新建账号的密码取环境变量 ZTB_PWD_<角色大写>
完成后汇报：账号池现状、能造到哪个阶段、哪些造不了及原因、需要我提供什么。
```

验证：`pytest testcases/baseline/trade/api -m p0 --env local`

主流程不用一次打通到最后：先打通近期需求要用到的阶段，后面的需求用到更靠后的阶段时，由 AI 接着补并登记。

## 样本库（接入时只备最少的，其余跟着需求按需提供）

接入时**不要求把样本备齐**。把所有可能用到的都列出来会有几十项，大部分近期用不到，人也提供不过来。分三类处理：

| 类别 | 是什么 | 什么时候、谁来做 |
|---|---|---|
| **AI 自己取** | 本系统页面接口的请求和返回（造数据要用）；能直接访问到的 WSDL（地址后加 `?wsdl`）；测试环境接口日志里的真实报文 | 页面接口：做「账号池和造数主流程」走页面造数时自动录下，不单独抓。真实报文：测试环境验证时，只读触发后从日志录制。**不列给人** |
| **接入时人提供（最少集）** | 环境地址和账号（已在 `project.yaml`）；本项目几乎每个需求都要用的一两样，如一份正常招标文件、一组正常投标文件 | 接入时，只列确实挡住基线冒烟的，一般不超过 5 项 |
| **按需提供** | 异常场景的投标文件、资审或答疑文件、各类异常报文、控件抓包、第三方安装包和证书、未开启功能（如评标主动推送）的资料 | 某个需求用到时，在该需求 `01_确认项.md` 的「测试准备」里列出，只列这个需求要的 |

```markdown
任务：盘点样本库。只修改 ztb_autotest/samples 目录。
1. 执行 python -m common.samples，了解现状
2. 输出「接入时需要提供的最少清单」：只列不提供就挡住基线冒烟或造数据主流程的，不超过 5 项；
   每项写明要什么、应放的路径、怎么取、挡住什么
3. 以下不要列进给人的清单：
   - 本系统页面接口的报文——在造数主流程走页面时自动录制，**不列进给人的清单，也不记进待取清单**
   - 你自己能取到的（能访问到的 WSDL、接口日志里的报文）——直接去取，取到后登记；
     当前环境取不到的，记到 samples/待取清单.md，写明到哪个环境、什么时机去取
   - 异常场景、可选功能、近期没有需求会用到的——不列，等需求用到时在该需求的确认项里提
   - 环境地址和账号——这是 project.yaml 的事，缺就按环境预检的提示处理
4. 用户提供后：放到对应目录，在 samples/index.yaml 登记，再执行一次检查
不要自己生成或伪造样本文件。
```

**全部完成后**：运行 `pytest -m p0`，跑不通的用例把报错发给 AI，「结合源码分析原因并修复」。冒烟跑通后，项目即可按三步法处理需求。
