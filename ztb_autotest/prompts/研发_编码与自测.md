# 提示词：研发编码与自测（AI 编码时使用）

使用人：研发。**先按 `01_确认项.md` 编码，再读 `02_测试用例.md` 自测**：编码时不看用例，用例才能独立检验代码有没有理解错；同时研发不用等用例生成完，确认项答复完就可以开工，和交付生成用例并行进行。

```
01 确认项答复完 ──┬── 研发：阶段 1 编码（依据确认项）──┐
                  └── 交付：第二步生成 02 测试用例 ────┴── 阶段 2 准备测试支撑 → 阶段 3 自测循环 → 阶段 4 自测报告
```

**核心规则：测试是标准，代码去满足测试；不能为了通过而修改测试。**

**依据优先级**（从高到低，高的覆盖低的，**不算冲突，不要再问**）：
1. `01_确认项.md` 中已填写的答复：方案结论、阻塞问题答复、关键场景示例 ✘ 的正确预期、补充口径 K 表
2. `02_测试用例.md` 的预期结果（阶段 2 起才读）
3. 需求文档原文（docx）——只在 1、2 都没有写到时才用

用例或确认项与需求原文不一致，而确认项已有答复时，按确认项执行，在自测报告附录记一句即可。
02 写了确认项没写的细节（如标点、换行）时，按 02 改代码，不用问。
只有 1 和 2 互相矛盾、或者都没写到时，才算「预期可能有误」，需要停下来问。

| AI 可以改 | AI 不能改（需要先停下来问） |
|---|---|
| 源码工程中的业务代码 | `testcases/` 中的断言和预期 |
| 测试脚本中的 `TODO`（选择器、接口地址、表名） | `02_测试用例.md` 中的预期结果 |
| 已实现的依赖项对应的 `xfail` 标记（删除） | 把失败用例改成 skip / xfail |
| 源码工程中本需求的单元测试（新增或补充） | |
| 服务端 mock、造数等测试支撑代码（只动自己造的 `AUTO_` 数据） | `testcases/baseline/` 产品基线用例 |
| | **已有业务数据**：不删除、不修改、不为复位而清空；不执行改表结构的 SQL |
| | 被框架拦截的写操作（`WriteBlocked`）、只读环境：不要绕过 |
| 脚本笔误：转义、引号、拼写错误，导致断言与 `02_测试用例.md` 预期不一致（修后要与 02 原文一致，在自测报告「脚本修正」中逐条列出） | 改变断言的含义（放宽、删减、换预期值） |

按阶段使用，**每个阶段一个会话**，完成后提交一次。也可以用末尾的合并版一次完成。

**必须停下来等用户回复的情况**（不是汇报后继续，而是停止本次回复）：
1. 编码前检查、自测前检查不通过
2. 每个阶段结束（**连续模式下不停**，见下）
3. 设计方案没写明、需要自行决定
4. 预期可能有误，或需求 / 设计未覆盖
5. 环境问题：服务未启动、地址不通、数据库连不上、账号登录失败、pytest 以「环境未配置」「没有用例」退出。**环境问题不属于脚本问题，不要自己改 project.yaml、不要猜地址、不要尝试启动服务、不要反复重跑**

6. 阶段 3 中同一个失败连续 3 轮修不好
7. 需要改动已有业务数据、需要执行迁移脚本（新增字段等）、或写操作被框架拦截（`WriteBlocked`）：说明要动什么数据、为什么，由用户确认或手工执行

检查发现的问题**一次问完**，不要分多轮问。

**进度必须可见、可续跑**（每进入一个新阶段、以及每次停下来之前都要做）：
1. 更新任务清单（工具自带的待办 / todo）：已完成的阶段标完成，当前阶段标进行中。清单只在你更新时才会变，不更新用户就以为还停在前面
2. 输出一行进度：如「阶段 2 完成：补全 12 处 TODO，冒烟 5/5 通过」
3. 更新 requirements/<需求名>/自测进度.md：当前阶段｜已完成的事｜未解决的失败及已试过的办法｜已定性的用例｜下一步
会话中断或用户说「继续」时：**先读自测进度.md 和 run_req.py --status**，从记录的位置接着做，不要从头再来。

**省时间的工作习惯**：
- 看源码、看文件用读文件和搜索工具，不用命令行（cat / grep / sed / find）：命令行每次要十来秒，专用工具不到一秒
- 能一次读完的文件一次读完，不要分很多小段读；同一个文件不要反复读
- 不要用重跑来「看一眼」：结果在日志文件里

**连续模式**：用户说「连续执行，阶段间不停」时：
- 阶段结束更新任务清单和自测进度.md、输出一行进度（如「阶段 1 完成：补改 3 个实施点，改动 4 个文件」），然后直接进入下一阶段，不等「继续」
- 上面第 1、3、4、5、6、7 种情况照常停下；停下时说明停在哪个阶段、卡在什么、需要谁提供什么，答复后从停下的位置接着跑
- 阶段 1 必须先完成并输出实施点核对清单，之后才能读取 02_测试用例.md（同一会话中也要遵守这个先后顺序）
- 一路跑到阶段 4 输出自测报告为止；所有中途的进度和修改都汇总进自测报告，不另外长篇汇报

---

## 编码前检查（阶段 1 之前，不通过就停）

```markdown
逐项汇报 ✔/✘：
1. 需求目录是 requirements/<日期_需求名>/，其中只有一份 01_确认项.md（有多份时停下来问用哪份）
2. 01_确认项.md 关键场景示例已逐行确认、没有「【待定】」的方案结论（保留【默认】的视为同意）
3. 源码工程路径可访问
不检查 02_测试用例.md 和环境——编码阶段不需要它们。
```

## 阶段 1：核对与补齐编码（依据确认项，不读用例）

**不是从零开始写**：研发通常已经手工或在另一个会话中写了代码。本阶段先核对已有改动，只补没做的部分。
用户说「已编码完成」「跳过阶段 1」时，不做本阶段，直接进入自测前检查。

**代码状态由用户在提示词里说明**，不要自己通读源码去判断；用户没说时问一次「代码状态是：已编码完成 / 写了一部分 / 还没编码？」再继续。

**核对做多细，按情况选，不要每次都逐点通读源码**（通读很慢）：

| 情况 | 做法 | 耗时 |
|---|---|---|
| 用户说已编码完成 | **跳过**。漏做的实施点会在自测中以用例失败的形式暴露，再补 | 无 |
| 源码在 git 中、能看到本需求的改动 | **快速核对**（默认）：只看 `git diff --stat` 和改动文件名，把实施点和改动文件对一遍，只列出「看不到对应改动」的实施点并补上；不逐行读代码，不输出完整核对表 | 几分钟 |
| 没有任何改动 | 不用核对，直接按确认项编码 | — |
| 用户明确要求「完整核对」，或源码不在 git 中又没说是否已编码 | 按下面的步骤逐点核对 | 较长 |

快速核对拿不准某个实施点是否已实现时，不深挖，记为「待自测验证」，由阶段 2 的冒烟自检确认。

```markdown
先完整阅读 ztb_autotest/AGENTS.md。
任务：核对并补齐需求 <需求名> 的编码。
- 唯一依据：ztb_autotest/requirements/<需求名>/01_确认项.md 中的方案结论、答复、关键场景示例（✘ 的按正确预期）、补充口径 K 表
- 需求原文只用于确认项没写到的地方
- **不要读取 02_测试用例.md 和 ztb_autotest/testcases/ 下本需求的脚本**，避免照着用例写代码
步骤：
1. 整理「实施点清单」；**完整核对时**逐条核对源码现状（快速核对按上表，只列看不到改动的），输出：实施点｜依据编号｜改动位置｜现状（已实现 / 部分实现 / 未实现）｜判断依据
   - 源码在 git 中：先看 git status / git diff 找出已有改动
   - 不在 git 中：直接读改动位置的代码判断，不要假设没改过
2. 输出清单后**不用停**，直接补「部分实现 / 未实现」项；已实现的不重写、不重构
3. 判断不准是否已实现时，按「部分实现」处理：只补缺的部分，不推翻已有写法
4. 每完成一个实施点，说明对应哪些关键场景示例（E01…）
5. 只改与本需求相关的代码；改动公共方法、公共组件时，先列出所有调用方
6. **可测试性**（本次新写或改动到的对接代码才要求，不借机重构旧代码）：
   - 调用其他团队系统的代码走一层适配，对方地址从配置读取，不写死——这样本地才能指向 mock
   - 浏览器控件（NTKO、签章等）保存后的逻辑（存附件、转换、改状态）放在**我们应用的服务端接口**里触发，接口参数明确、脚本可直接调用；不要靠控件页面里的前端脚本一步步驱动
   - 确认项的方案与这两条冲突，或现有实现不满足且改动较大时，不要自行改，在核对清单中标「可测试性缺口」并停下来问
7. 设计方案没写明、需要你自行决定的地方，先停下来问我
8. 纯逻辑规则（校验、计算、判定、取值）在源码工程中补单元测试，用项目现有的单元测试框架和目录；项目没有单元测试框架时不要引入，在清单中说明即可
9. 完成后列出本次改动的文件清单（区分「原已实现」和「本次补改」）
```

## 自测前检查（阶段 2 之前，不通过就停）

```markdown
执行一条命令做准备度检查，把输出原样汇报：
  python tools/preflight.py --env <环境> --req <需求目录名>
它会检查：本需求用到的配置、被测服务能否访问、数据库能否连接、浏览器是否可用、登录页对象是否已补全、用例能否收集。
- 全部 ✔：进入阶段 2
- 有 ✘：**停下来**，把 ✘ 清单交给用户处理。这些是准备工作，不要在自测会话里自己解决——
  不安装或下载浏览器、不配置环境、不找测试数据、不摸索登录页、不执行迁移脚本
- 登录页对象仍有 TODO：说明项目还没接入，请用户先做一次项目接入（prompts/00_新项目接入.md）；本需求没有界面用例时可以继续
同时确认：requirements/<需求名>/02_测试用例.md 存在，其第六节要求的测试数据已提供；从 02 第三节「模块」列列出涉及的模块。
02 还没生成时：汇报「编码已完成，等待测试用例」，然后停止。
**连续模式只在准备度检查全部通过后才开始**；检查不通过时即使用户要求连续执行也要停下。
```

## 阶段 2：准备测试支撑

```markdown
先完整阅读 ztb_autotest/AGENTS.md。
任务：为需求 <需求名> 准备测试支撑。
读取 ztb_autotest/requirements/<需求名>/02_测试用例.md 的「五、mock 方式」「六、测试数据与环境」「八、遗留事项」，完成：
1. 先看 02 附录 D「编码后落地清单」：这些是生成用例时代码还没写、留到现在补的。逐条补全后在清单上标 ✔；补不了的说明原因
   补全 ztb_autotest 中本需求脚本和页面对象的 TODO（选择器、接口地址、表名），依据源码（含阶段 1 的改动），注明文件路径
2. 用例需要服务端 mock 时：在 ztb_autotest/mocks/ 实现对应 mock 服务（参考 eval_mock_server.py 和 mocks/README.md，支持按场景切换），
   并在源码中确认第三方地址是否可配置；不可配置的，列出需要改哪个配置项
   - mock 数据取自样本库：先看 samples/index.yaml 和 samples/messages/<依赖>/<接口>/ 是否已有需要的场景；没有时请用户从测试环境接口日志中提供（脱敏），放进样本库并登记；拿不到时先手写，来源标「手写，待录制」，并在自测报告中注明
   - mock 只在本地启动；不要修改测试环境的第三方地址
3. 控件类用例（控件之后的逻辑）：在源码中找到控件保存时上传到我们应用的接口，用样本库中的文档样本（samples/files/doc/）直接调用；
   样本库里有控件保存请求的抓包（samples/third_party/<控件>/）时以它为准；缺样本时向用户要，不要自己伪造文档；
   找不到可直接调用的接口时，不要模拟控件，列为「可测试性缺口」并说明现状（后续逻辑由哪段前端脚本驱动）
4. 用例需要前置数据或账号时先读 flows/造数能力.md：能造的直接造；链条不够长就补进 flows/ 并登记；账号池不够按登记的方法补。
   长流程的前置数据（如标后需求要「已定标」）按 AGENTS.md「长流程的前置数据」：本系统步骤走接口、外部结果扮演对方、走不通的那一步才写库快进（照源码写全，登记绕过了什么）；
   新阶段补进 flows/project_flow.py 的 STAGES 和 reach，不在需求脚本里另写一套
   不要因为缺数据就把用例 skip 掉等人提供——本地能造的必须造出来；确实造不出来的，报告中记为「未完成」而不是「跳过」
   只在自己造的 AUTO_ 数据上操作页面（有些按钮会隐式保存）；造出可复用的数据状态后整理进 flows/ 并登记，不要只留在 .runtime/probe/
   用例需要特定数据状态时，按下面的顺序选择，**不得为了复位而删除或修改已有业务数据**：
   a) 新造一条 AUTO_ 前缀的数据（首选）
   b) 使用 project.yaml 的 test_data 中登记的专用测试项目
   c) 只能用已有数据时：停下来说明要动哪张表、哪些记录，用户确认后才做；fixture 先备份、结束后还原，只按主键操作
   需要新增字段等表结构变更时，不要自己执行，告诉用户要执行哪个迁移脚本
5. 02 中执行环境为「单元测试」的用例：对照源码工程中的单元测试，已有的在用例编号旁注明对应的测试方法；没有的按 02 的预期补上。
   项目没有单元测试框架时，改用接口层自动化验证并在自测报告中说明，不要引入新框架
6. **冒烟自检**（跑界面用例之前必须做，几分钟内完成）：对 01 的每个实施点，用最直接的方式验证一次「功能确实生效」——
   调接口后查库、或直接查接口返回，不走界面。例如新增字段：保存一次，查库确认值已写入。
   - 冒烟不过说明编码未完成，属于业务代码问题：先修代码，不要带着它去跑界面用例
   - 结果列成表：实施点｜验证方式｜结果
7. 摸索页面的规矩：
   - 登录、菜单、通用控件在项目接入时已经学过，自测中不再学；准备度检查第 5 项是 ✘ 时停下，请用户先做项目接入
   - 先看 pages/ 下已有的页面对象、通用方法和 pages/环境差异.md，能复用就不摸索；通用方法里缺的控件操作，补进通用方法而不是只写在本需求的页面对象里
   - 确实要摸索时，临时脚本放 .runtime/probe/，不放 tools/、common/（框架层，升级会覆盖）；摸清一个控件的操作方式后**立即写进页面对象**，同类控件不再重复摸索
   - 浏览器一律无界面运行，不加 --headed；不执行 playwright install
完成后列出修改清单、仍无法完成的事项和原因。不要修改任何断言。
```

## 阶段 3：自测循环

```markdown
任务：运行需求 <需求名> 的自动化用例并修复，直到通过。
**一律用运行器，不直接敲 pytest**：它把完整输出存进日志，只返回失败摘要（断言信息和位置），并记录每条用例失败了几轮。
1. 首次：python tools/run_req.py --req <需求目录名> --env <环境>
2. 之后每轮**只重跑失败的**：python tools/run_req.py --req <需求目录名> --env <环境> --failed
   - 摘要不够判断时，直接读摘要末尾给出的日志文件，**不要为了看报错而重跑**，不要用 tail / grep 截取输出
   - 只想验证某一条：加 -k "<用例编号>"
3. 对每个失败按「依据优先级」判断原因，分四类处理：
   a) 业务代码问题（代码与 02 预期不符，且 02 不与确认项矛盾）→ 修改源码
   b) 测试脚本问题（选择器、TODO、笔误）→ 修改脚本，但不能改变断言含义，并说明修改内容
   c) 02 预期与确认项矛盾，或两者都没写到 → 不修改，**立即定性**，之后不再重跑它：
      python tools/run_req.py --req <需求目录名> --classify "<用例编号>=c:<一句话原因>"
   d) 环境问题（连不上、超时、登录失败、「环境未配置」）→ 不修改任何文件，定性为 d 并停下来说明缺什么
   定性后的用例运行器会自动排除。c 类不用马上停：继续处理其他失败，最后在报告中一并列出；d 类立即停
4. **同一条用例连续失败 3 轮即停**：运行器会标出「已连续失败 3 轮」，此时不要再试，说明试过什么、卡在哪里，由用户决定
5. **不算失败**：摘要中「待其他环境执行」的用例，是当前环境不提供该外部系统而跳过的，原样记入自测报告，
   不要为了让它在本地跑起来而改标签、改配置或模拟控件
6. 已实现的依赖项对应的 xfail 标记删除，让它正常执行
7. 02 中「单元测试」的用例：用项目的构建工具运行对应的单元测试（只跑本需求相关的测试类），失败同样按四类处理
8. 本需求没有未解决的失败后：
   - 涉及的每个模块跑一次回归：python tools/run_req.py --req <需求目录名> --env <环境> --module <模块>
   - 最后做**一次**最终全量：python tools/run_req.py --req <需求目录名> --env <环境> --all
   全量很慢，只在这时跑一次，中途不要跑全量
```

## 阶段 5：测试环境验证（部署后，可由交付执行）

本地自测通过不等于对接没问题：mock 是按我们的理解做的，真实系统只在测试环境有。

```markdown
任务：需求 <需求名> 已部署到测试环境，做测试环境验证。
1. 执行 pytest --req <需求目录名> --env test
   - 测试环境是共用的、只读的：只触发业务、只查数据，不复位、不清理、不改任何配置
   - 只使用专用测试项目（project.yaml 的 test_data 或 02 第六节指定的数据）
2. **界面用例在测试环境失败、而本地是通过的**：先判断是不是环境差异（测试环境和开发环境大体一样，细节会不同，如接了统一登录、
   多一个安全提示弹窗、控件样式不同）。到测试环境的真实页面上看一眼再下结论：
   - 是环境差异 → 不用停，当场补进通用方法（pages/login_page.py、pages/base_page.py）：
     在 project.yaml 测试环境的 ui 一节加一个选项，方法里用 self.ui_option 取，默认值保持开发环境的做法；
     登记到 pages/环境差异.md；回到本地重跑一条用到该方法的用例，确认没有改坏；结果里写一句「沉淀环境差异 E0x：……」
   - 通用方法里没有、测试环境才有的页面或弹窗（如统一登录页）→ 同样补进通用方法并登记，不要只写在本需求的脚本里
   - 页面和操作都一样、只是结果不同 → 不是环境差异，可能是缺陷或数据问题，按阶段 3 的四类处理，不要用环境分支绕过去
   - 测试环境学习页面时只浏览和操作控件，不保存、不提交、不改数据
   - 对接真实外部系统的用例跑通后，把这次的真实请求和返回报文脱敏存进样本库，替换同场景「手写，待录制」的样本，并更新 samples/index.yaml 的来源
3. 对接真实外部系统的用例失败时，先比对真实返回报文与 样本库 samples/messages/ 中的报文：
   - 报文结构变了 → 对方接口有变更，停下来说明差异，由用户与对方团队确认后更新录制和代码
   - 结构一致 → 按阶段 3 的四类处理（修代码需要重新部署）
4. **测试环境或人工复核发现的问题要和用例闭环**（本地全过、到这里才发现的，每一个都要处理到底）：
   a) 先判断属于哪一类，再按类处理：
      - 有用例但本地通过、这里失败 → mock 或本地数据与真实情况不一致：修代码或修 mock，把真实报文存进样本库替换手写样本
      - 没有用例覆盖 → **先补一条能复现它的用例**（写进 02，标 🆕，定好执行环境），确认新用例失败，再修代码，直到通过
      - 用例的预期本身不对，或确认项没问到 → 停下来，由交付在 01_确认项.md 追加或更正（标 🆕），再改用例和代码
      - 环境差异 → 按第 2 条沉淀
   b) 每个问题记一行到 requirements/<需求名>/03_验收记录.md（按 docs/模板/03_验收记录模板.md，标返工分类和关联用例）
   c) 同一类问题以后别的需求也会遇到的（如某类控件总漏测、某类数据总缺），在 docs/改进建议.md 追加一行
      「现象｜建议改哪条规则或提示词｜来自哪个需求」。**只提建议，不自行修改 AGENTS.md 和 prompts/**，由人确认后再并入
5. 在自测报告中追加「测试环境验证」一节：自动用例结果、本次沉淀的环境差异、人工验收清单的执行情况（由交付填写）
```

## 环境说明

- 研发本地自测：在 `project.yaml` 的 `envs` 中配置 `local`（本地启动的服务地址），执行时加 `--env local`；`local` 默认是注释掉的，不取消注释并填写就会在自测前检查时停下
- 测试环境验证：部署后执行 `--env test`，只读；对接真实外部系统的用例在这里跑
- 外部依赖：每个环境在 `project.yaml` 的 `deps` 中声明评标系统、控件等是 mock、真实、人工还是没有；当前环境不提供的用例自动跳过，不算失败
- 口令：只通过环境变量提供（`ZTB_PWD_<角色>`、连接串中的 `${ZTB_DB_PWD}` 等），不写进任何文件和报告
- 不需要告诉 AI 模块名：本需求用例按需求目录名（`--req`）筛选，涉及哪些模块由 AI 从 02 中读出
- 开跑前先过准备度检查：`python tools/preflight.py --env local --req <需求目录名>`，人也可以自己先跑一遍，把 ✘ 处理掉再让 AI 开始
- 浏览器：自动选择「Playwright 自带 Chromium → 本机 Chrome → 本机 Edge」，不下载；无界面运行，另起独立进程，不影响你正在使用的浏览器
- 登录：每个角色整次运行只登录一次（`page_as("agent")`），不是每条用例都登录
- 人工验收项（真机、真实第三方、视觉效果）不在自测范围内，由交付在验收时完成
- **建议编码和自测用不同的会话**：编码会话没看过用例，自测会话按用例检验，理解偏差才能暴露出来
