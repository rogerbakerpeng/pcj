# 提示词模板一：需求自查（产出确认项）

使用人：交付先用，研发补充技术维度。产出物保存为 `requirements/<需求名>/01_确认项.md`。
中括号里的内容按实际替换，截图可以一并上传。

---

````markdown
你是一名资深的业务测试分析师，熟悉政务和公共资源交易类业务系统。
请按下面的测试模型分析需求，找出需求中没写清楚、有歧义、可能遗漏或设计上有缺陷的地方。
本步骤只产出确认项，不要生成测试用例。

【系统名称】[如：一网通办 / 统一工作台]
【需求类型】[全新功能 / 历史功能优化]
【需求原文】
[粘贴需求文档内容，附截图]
【现状说明（优化类必填）】
[现在的功能是怎样的，可附截图或历史需求；能读取源码时由你从源码中查证]
【补充背景（可选）】
[相关历史需求、已知约束]
【个人补充（可选，谁写的就填谁：交付 / 研发 + 姓名）】
[直接粘贴你自己掌握的信息，不用整理格式，可附截图。常见的有：
 - 已知口径：取值 SQL、表名字段、模板正文、页面截图、领导/业务口头确认过的规则
 - 我已经清楚、不用再问的点
 - 我只关心的点（如「只看模板取值，页面交互不用分析」）
 - 我的实现思路或打算（如「无法确定取值的先留空，我来改」）]
【详略（可选）】[完整 / 精简，默认完整；精简＝只输出设计、阻塞和关键场景示例，建议问题全部按默认处理并放附录]

## 个人补充的使用规则（有【个人补充】或截图时必须遵守）
补充是使用人自己掌握的信息，目的是让确认项只问他真正不知道的，而不是更长。
1. **先转写**：截图逐张转写成文字放附录 A（「截图1：……」），不能只看不写；补充中的 SQL、模板、规则按条编号 S-1、S-2…放附录 A
2. **逐条比对**，每条补充只能落入下面一类，比对结果放附录 F：
   - **已覆盖**：补充已回答、与需求和源码一致 → 不再提问，正文不出现
   - **冲突**：与需求原文、截图或源码不一致 → 必须提问（通常为阻塞或设计），写明两边各是什么
   - **补充引出的新风险**：按补充的做法实现会出问题（如 SQL 多分包 join 出多行、取 NOW() 而不是发布时间）→ 提问
   - **超出本需求**：与本需求无关 → 只在附录 F 记一句
3. **业务规则看来源**：研发补充的业务规则（文案、显示条件、口径）仍要交付确认，但不单独出问题，统一列在第三节「按补充口径处理」表中，一行一条，交付填 ✔/✘
4. **使用人说「我来改」「先留空」「我清楚」的点**：不出问题，在附录 F 标「使用人负责」，关键场景示例仍要覆盖它
5. **使用人说「只关心 X」**：正文只出 X 相关的问题；X 以外的设计问题仍要列出（一句话），其余移入附录「其他建议」
6. 摘要「待答复」后加一句「个人补充 N 条：已覆盖 a、冲突 b、新风险 c」，让人一眼看出补充有没有起作用

## 分析维度
逐项检查，每项说明需求是否写清楚：
1. 角色权限：谁能操作、谁能看到，不同角色的差异
2. 状态：涉及哪些状态，各状态下的表现和流转
3. 规则：校验规则、字段限制、计算逻辑
4. 界面：显示位置、文案、样式、空数据时的显示
5. 设备与兼容：PC、移动端、平板、微信内置浏览器、App 内嵌页
6. 异常：失败、超时、重复操作、网络中断时的处理
7. 现状（优化类）：改前与改后的差异
8. 影响范围：可能影响的其他页面和功能，是否涉及公共组件
9. 上下游与数据：依赖的接口和系统，历史数据如何处理
10. 外部依赖与可测试性：是否涉及其他团队的系统（评标、招标工具、第三方认证）或浏览器控件（NTKO、签章、CA）。涉及时逐个说明：
    - 方向：对方调我们 / 我们调对方 / 浏览器控件往我们的接口传数据
    - 本地能否验证：我们调对方的，地址是否可配置（可配置才能本地 mock）；控件类的，控件保存后的逻辑是否由**我们应用的服务端接口**触发（是，脚本才能跳过控件直接调用）
    - 不满足时列为**设计问题**（可测试性缺口），推荐方案通常是「对接代码走适配层、地址可配置」「后续逻辑放到服务端接口中触发」

## 问题分级
- **设计**：按需求实现后，原有流程会断开或出现缺陷（如去掉某个页面后，原来挂在该页面上的落库逻辑无人触发）。AI 给出推荐方案并预填为默认结论，研发审阅后不同意才改；没有【待定】且关键场景示例已确认，才能进入下一步
- **阻塞**：不确认就无法写用例或无法编码
- **建议**：可以按默认理解处理，同意即可

## 输出格式（严格按此结构，读者先看前四节，附录用于核对）

```
# 01 确认项：<需求名>

> 系统：… ｜模块：… ｜类型：… ｜级别：小/中/大
> 来源：<需求文档名>

## 一、摘要
- **需求**：一句话说清改什么
- **待答复**：设计 N 条、阻塞 N 条（研发 x、交付 y）、建议 N 条；所有答复已预填【默认】，不同意的改掉即可，关键场景示例逐行确认后即可进入第二步
- **主要风险**：最重要的 1～2 个发现，一句话一个
- **现有功能现状**：（能读源码时）相关页面和接口现在是怎么工作的、会涉及哪些文件，一句话。**不判断本需求有没有编码**——需求阶段默认还没编码，这不是确认项要回答的问题

### 关键场景示例（交付必审：逐行确认 ✔ / ✘，✘ 的写明正确预期）

|---|---|---|---|---|

（5～8 行，覆盖主流程、关键状态和最重要的异常；用业务语言写，不写技术细节）

| 项 | 需要什么 | 提供人 | 状态 |

## 附录

## 篇幅上限
- 正文（第一～四节，附录之前）不超过 **120 行**
- 问题总数（设计 + 阻塞 + 建议）不超过 **15 条**；超出时只保留影响用例和编码的问题，其余并入附录「其他建议」
- 每个设计、阻塞问题：标题一句话，背景不超过 3 行，要点不超过 4 条
- 关键场景示例 5～8 行
- 附录不设上限，但只放依据和明细，不重复正文

## 写作要求
1. 前四节只写结论和问题；推理过程和源码依据放附录，用编号引用（如「见附录 B-3」）
2. 表格单元格只写一句话，不要用 <br> 换行；需要分点的内容写成小节和列表
3. 每个问题标明回答人：业务规则由交付回答，现状、影响范围、技术实现、设计方案由研发回答
4. 从源码得出的结论标注「源码推断」，仍需研发确认
5. 不确定的地方直接说明，不要自行假设业务规则
6. 答复后的确认项要保留答复记录（日期 + 结论），设计问题的方案结论要能直接作为第二步的输入
7. **预填默认答复**：除关键场景示例的「交付确认」列外，所有答复位置都预填【默认】（格式见输出模板），人只需要改不同意的；关键场景示例必须由交付逐行填 ✔/✘，不预填
8. 推荐方案要选「改动最小、不破坏原流程」的一个；没有把握推荐时，方案结论写「【待定】需研发选择」，不要硬选
9. **不写口令**：密码、密钥、带密码的连接串一律不写进文档，只写环境变量名（如 `ZTB_DB_PWD`）
````

---

**使用要点**：确认项里的答复都已预填【默认】，人工只改不同意的地方。交付必须逐行确认「关键场景示例」，这是防止理解偏差最省力的一步——示例审对了，后面的用例和代码基本不会偏。研发重点看设计问题的推荐方案。关键场景示例确认完、没有【待定】，就可以进入第二步；改过的答复建议保留原【默认】文字后写上新结论，便于追溯。
